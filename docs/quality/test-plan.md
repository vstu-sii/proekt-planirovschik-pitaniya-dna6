# Test Plan — Quality & Safety

## 1. Назначение

План определяет проверки качества и безопасности для «Планировщика питания» и связывает их с PRD, success criteria и Golden Dataset Lab 2.

Главный принцип: LLM отвечает за смысл, рецепты и формулировки, а критические числовые и бизнес-ограничения проверяются детерминированно.

## 2. Unit tests

| Область | Что проверяется | Критерий |
|---|---|---|
| Cost | расчёт стоимости меню/корзины | корректность формулы и исходных данных |
| Nutrition | калории и БЖУ | корректность расчёта порций |
| Budget | превышение бюджета | корректное сравнение с лимитом |
| Restrictions | запреты/ограничения | 0 критических нарушений |
| Ingredient aggregation | объединение ингредиентов | одинаковые позиции агрегируются корректно |
| Inventory | учёт запасов | уже имеющийся запас не дублируется без необходимости |
| Schema validation | structured output | невалидный ответ не проходит дальше |
| Rescheduling | перенос блюда | план, покупки и расчёты согласованы |

## 3. Integration tests

Проверяются цепочки:
1. Mobile → Backend.
2. Backend → DB.
3. Backend → AI endpoint.
4. AI response → schema validator.
5. Structured result → deterministic calculations.
6. Изменение меню → пересчёт списка покупок.
7. Изменение меню → пересчёт бюджета.
8. Изменение меню → пересчёт КБЖУ.
9. Timeout/error AI → безопасный fallback/ошибка.
10. Health checks сервисов.

## 4. Golden Dataset / Evals

Файл: `docs/quality/golden-dataset/v1.jsonl`.

Версия содержит **35 кейсов**, что входит в требуемый диапазон Lab 2: 30–50.

Покрываются:
- генерация меню;
- быстрые блюда;
- покупки;
- запасы;
- остатки;
- бюджет и дешёвые замены;
- КБЖУ;
- персонализация;
- перенос блюд;
- prompt injection и indirect injection;
- критические пищевые ограничения.

Для каждого кейса проверяются `reference`, `context`, `checks` и `safety_level`.

### Важное правило eval

Нельзя требовать единственного буквального ответа LLM там, где допустимы разные корректные формулировки. Eval проверяет свойства результата: ограничения, структуру, наличие обязательных элементов, отсутствие запрещённых элементов и корректность переданного контекста.

## 5. Критерии качества из Lab 1

| Метрика | Порог |
|---|---:|
| Соблюдение жёстких ограничений | ≥98% |
| Бюджет | ≥95% |
| КБЖУ | ≥90% |
| Полнота меню | ≥95% |
| Корректность списка покупок | ≥95% |
| Использование продуктов из запасов | ≥95% |
| Сценарии остатков | ≥95% |
| Быстрые варианты | ≥90% |
| Тон/качество формулировки | ≥90% |
| Критические safety-нарушения | 0% |

Критические нарушения: нарушение аллергии/запрета, опасный совет или игнорирование критического ограничения.

## 6. Safety tests

Обязательные классы:
- прямой prompt injection;
- indirect injection через retrieved-контекст;
- попытка раскрытия system prompt;
- попытка раскрытия API key/token/секрета;
- excessive agency / произвольный tool call;
- обход бюджета;
- обход аллергии/запрета;
- невалидный structured output;
- ложная точность КБЖУ;
- oversized input и повторные запросы.

## 7. CI

На Pull Request:
- lint;
- format;
- unit tests;
- typecheck;
- проверка OpenAPI/schema;
- проверка JSON/JSONL;
- `docker compose config`, если Compose входит в PR;
- secret scanning;
- smoke eval на изменённых/критичных кейсах.

Перед merge должны быть зелёными обязательные проверки.

## 8. Nightly / полный прогон

Ночью или перед релизом:
- полный Golden Dataset;
- полный safety eval;
- integration tests;
- regression suite;
- performance checks;
- проверка SLO/SLA.

После изменения модели, prompt, RAG, AI API или Use Case полный eval запускается повторно.

## 9. SLO/SLA из PRD

| Сценарий | SLO | SLA |
|---|---:|---:|
| Генерация меню | p95 ≤10 с | 99% ≤15 с |
| Рецепт из остатков | p95 ≤5 с | 99% ≤8 с |
| Интерфейс/API | 99% ≤200 мс | — |
| Доступность | ≥99% | — |

## 10. Владельцы

- Quality & Safety — Test Plan, Golden Dataset, safety criteria и контроль регрессий.
- AI Engineer — AI/eval execution и исправление AI-related дефектов.
- Delivery — CI, integration и инфраструктурные проверки.
- Product VO — expected behavior Use Cases и приёмка пользовательского результата.

## 11. Release gate

Результат не считается готовым, если:
- есть критическое нарушение ограничения;
- AI output не проходит schema validation;
- обнаружена утечка секрета;
- модель получает недопустимые полномочия;
- нарушены согласованные SLO/SLA без зафиксированного решения;
- обязательный Golden Dataset/eval не проходит установленный порог.
