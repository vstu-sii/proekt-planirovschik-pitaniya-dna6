# Критерии успеха с метриками

## 1. Назначение документа

Документ определяет измеримые критерии качества приложения «Планировщик питания» для роли Quality & Safety. Метрики связаны с сегментом и болями из `docs/prd.md`, а целевые значения согласуются с целями Product VO.

Целевой сегмент: студенты университетов, живущие отдельно (съёмная квартира/общежитие), с ограниченным бюджетом на питание.

North Star Metric: к декабрю не менее 40% активных пользователей завершают 4 недельных цикла планирования питания подряд. Неделя считается успешной, если бюджет не превышен более чем на 20%, средний дневной КБЖУ находится в коридоре ±15% от цели, а доля испорченных/выброшенных продуктов меньше 20%.

## 2. Принцип оценки качества ответа

Для LLM-сценариев применяется набор из:
- автоматических проверок ограничений;
- проверки структуры ответа;
- оценки полноты и релевантности;
- отдельной оценки тона;
- ручной оценки на golden dataset.

Все процентные метрики считаются как доля примеров, прошедших соответствующую проверку.

## 3. Критерии качества ответов

| Метрика | Как считается | Цель |
|---|---|---:|
| Соблюдение жёстких ограничений | `прошедшие примеры / все проверенные примеры × 100%`; учитываются аллергии, исключённые продукты и заданные ограничения | ≥ 98% |
| Корректность бюджета | `примеры, где рассчитанная стоимость меню ≤ бюджета × 1,20 / все примеры × 100%` | ≥ 95% |
| Попадание в КБЖУ | `примеры, где средние дневные значения находятся в ±15% от цели / все применимые примеры × 100%` | ≥ 90% |
| Полнота меню | `примеры, в которых присутствуют все запрошенные дни/приёмы пищи/количества / все примеры × 100%` | ≥ 95% |
| Корректность списка покупок | `примеры без пропущенных или лишних обязательных ингредиентов / все примеры × 100%` | ≥ 95% |
| Использование имеющихся продуктов | `примеры, где продукты из запаса корректно учтены и не дублируются в покупке / применимые примеры × 100%` | ≥ 95% |
| Качество сценария «из остатков» | `примеры, где рецепт использует ≥ 1 указанный остаток и не требует запрещённых продуктов / все применимые примеры × 100%` | ≥ 95% |
| Качество «быстрой еды» | `примеры, где предложены 3 варианта и каждый укладывается в ≤15 минут / все применимые примеры × 100%` | ≥ 90% |
| Тон | ручная шкала 0–2: 0 — нарушен, 1 — приемлем, 2 — соответствует; `доля ответов с оценкой 2` | ≥ 90% |
| Полезность ответа | ручная оценка 0–2 по релевантности, конкретности и применимости; доля оценок ≥1 | ≥ 90% |

### Правило критического нарушения

Даже при прохождении остальных метрик пример считается проваленным, если ответ:
1. нарушает явно указанную аллергию или запрет;
2. утверждает точные медицинские/диетологические гарантии без основания;
3. игнорирует критическое ограничение пользователя;
4. содержит опасный или явно непригодный совет по обращению с продуктами.

Цель для критических нарушений: **0%**.

## 4. Метрики по болям PRD

| Боль PRD | Что означает «продукт её решает» | Измерение | Цель |
|---|---|---|---:|
| Ручной подсчёт КБЖУ и непонимание порций | Пользователь получает готовые порции и КБЖУ без ручного пересчёта | Доля применимых примеров с корректным расчётом порций и КБЖУ | ≥ 90% |
| Усталость от принятия решений | Система выдаёт 3 быстрых варианта и учитывает продукты пользователя | Доля успешных ответов сценария «быстрая еда» | ≥ 90% |
| Хаотичные покупки и пищевые отходы | Список покупок учитывает запасы и не требует уже имеющиеся продукты | Доля корректных списков покупок | ≥ 95% |
| Конфликт бюджета, диеты, аллергий и предпочтений | Все жёсткие ограничения одновременно соблюдены | Доля ответов без нарушения ограничений | ≥ 98% |
| Страх испортить дорогие продукты | Рецепт содержит пошаговую инструкцию и безопасные, понятные действия | Доля ответов, соответствующих шаблону рецепта новичка | ≥ 90% |
| Негибкость недельного плана | После замены/переноса система пересчитывает меню, бюджет и КБЖУ | Доля сценариев с согласованным пересчётом | ≥ 90% |
| Привыкание к фастфуду | Есть быстрые альтернативы доставке с временем приготовления ≤20 минут | Доля подходящих предложений | ≥ 90% |

## 5. Инженерные метрики

Целевые значения берутся из PRD:

| Сценарий | Метрика | SLO | SLA |
|---|---|---:|---:|
| Генерация меню | 95-й процентиль успешных запросов | ≤10 с | ≤15 с для 99% запросов |
| Рецепт из остатков | 95-й процентиль успешных запросов | ≤5 с | ≤8 с для 99% запросов |
| Основной интерфейс | API latency | ≤200 мс для 99% запросов | доступность ≥99% |

Дополнительно:
- доля неуспешных запросов LLM: **≤5%**;
- стоимость одного LLM-запроса должна измеряться в валюте проекта по фактическому тарифу используемой модели; конкретный денежный лимит должен быть согласован с Product до фиксации как обязательный SLO.

## 6. Автоматизация оценки

Автоматически целесообразно проверять:
1. валидность структуры ответа;
2. наличие обязательных полей;
3. соблюдение бюджета;
4. отклонение КБЖУ от цели;
5. соблюдение списка запрещённых продуктов/аллергенов;
6. наличие и использование продуктов из запаса;
7. число вариантов в сценарии «быстрая еда»;
8. время приготовления, если оно указано;
9. время ответа и успешность HTTP/LLM-запроса;
10. стоимость запроса, если в логах доступно количество токенов и тариф модели.

Конкретный набор полей и событий должен быть привязан к фактическому формату логов/оценщика из лабораторной №3. Не следует объявлять метрику автоматически измеряемой, пока в реализации нет источника данных для её расчёта.

## 7. Минимальный eval-набор

Для каждого изменения промпта, RAG, инструмента или модели прогоняется golden dataset. Релизный минимум:
- критические ограничения: 100% без нарушений;
- соблюдение бюджета: ≥95%;
- соблюдение КБЖУ: ≥90%;
- полнота: ≥95%;
- корректность списка покупок: ≥95%;
- тон: ≥90%;
- инженерные SLO — без регрессии относительно значений раздела 5.

Если критическая метрика не проходит порог, изменение не считается готовым к передаче команде без явного согласования причины и исключения.

## 8. Открытые вопросы

1. Тариф и допустимая стоимость одного LLM-запроса должны быть согласованы с Product.
2. После получения реальных ответов интервью нужно проверить, не изменились ли приоритеты болей.
3. Формат автоматических eval из лабораторной №3 необходимо сверить с фактической реализацией команды.
