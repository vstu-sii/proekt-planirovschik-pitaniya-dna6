## 1. Идентификация
- **UC-1.** Настроить профиль
- **Основной актор:** Пользователь
- **Дополнительные акторы:** Сервис профиля, База данных профилей
- **Триггер:** пользователь открывает «Настроить профиль» при первом входе или «Мой профиль → Настройки питания».
- **Приоритет:** Высокий
- **Частота:** 1 раз при первом входе, 1–2 раза в месяц при редактировании

## 3. Предусловия и выходные условия
**PRE-1.** Пользователь авторизован.  
**PRE-2.** Есть доступ к API сохранения профиля (иначе сохраняемый черновик не подтверждается сервером).

**POST-1.** Валидный профиль сохранён в БД и привязан к `user_id`.  
**POST-2.** Сохранённые ограничения применяются при следующей генерации меню (UC-3).  
**POST-3.** При ошибке валидации/сохранения профиль не считается обновлённым; пользователь получает понятную причину.

## 5. Контракт интерфейса / API (v3)

| Операция | Контракт | Успех | Ошибки |
|---|---|---|---|
| Получить профиль | `GET /profile` (или эквивалент) | `200` + текущий профиль/пустая структура | `401` не авторизован |
| Сохранить/обновить профиль | `POST/PUT /profile` с телом профиля | `200/201` + сохранённый профиль, `saved_at` | `400` валидация, `401` auth, `409` конфликт версий/дубликат при наличии, `503` временно недоступно + `request_id` |
| Рассчитать КБЖУ | `POST /profile/target-nutrition` или локальный расчёт с серверной валидацией | `200` + целевые КБЖУ/БЖУ | `400` недостаточно данных |

> Реализация может использовать другие пути, но должна сохранять семантику: авторизация обязательна, валидация серверная, ошибки машинно-различимы, технический сбой не маскируется под успех.

## 6. Основной сценарий
1. Пользователь открывает раздел профиля.
2. Система показывает текущие значения или пустую форму.
3. Пользователь заполняет бюджет, параметры тела, активность, время приготовления, цель.
4. Система рассчитывает целевое КБЖУ и показывает его до сохранения.
5. Пользователь подтверждает КБЖУ, выбирает аллергены/предпочтения.
6. Пользователь нажимает «Сохранить».
7. Система выполняет серверную валидацию, сохраняет профиль в БД.
8. Система подтверждает сохранение и показывает, что ограничения применятся в следующей генерации.

## 7. Альтернативы и исключения
- **A1. Редактирование:** изменяются только переданные/изменённые поля; неизменённые значения сохраняются.
- **E1. Некорректный бюджет:** `budget_week_rub <= 0` или невалидный формат → `400`, сообщение «Укажите бюджет больше нуля», профиль не сохраняется.
- **E2. Конфликт аллергенов/предпочтений:** несовместимый выбор → `400`/валидационная ошибка с конкретным конфликтом; сохранение блокируется до исправления.
- **E3. Недоступно сохранение:** сеть/БД/сервер недоступны → `503` + `request_id`, профиль не помечается как сохранённый.
- **E4. Не заполнены критически важные поля:** отсутствуют обязательные поля → `400` со списком полей.

## 8. Правила валидации и безопасности
- Валидация выполняется на сервере; клиентская валидация только для UX.
- Нельзя сохранять профиль без `user_id` из доверенной сессии.
- Аллергены и предпочтения принимаются только из allowlist справочников.
- Несовместимые предпочтения/аллергены не сохраняются «тихо».
- Ошибки не должны раскрывать внутренние детали БД/стека.

## 9. Критерии приёмки (G1/G3)

| ID | Гейт | Критерий приёмки | Проверка |
|---|---|---|---|
| AC-UC1-01 | G1 | Некорректный бюджет (`<=0`, пусто, нечисловое) отклоняется; валидный сохраняется | UI + API тест, BUG-001 |
| AC-UC1-02 | G1 | Профиль сохраняется в БД и доступен после новой сессии/перезагрузки | E2E + DB-check, BUG-006 |
| AC-UC1-03 | G3 | Целевое КБЖУ/цель рассчитывается и используется как ограничение генерации | E2E UC-1→UC-3, BUG-004 |

## 10. Наблюдаемость и NFR
- Время отклика интерфейса ≤ 200 мс для локальных операций формы; сохранение — в пределах общего API SLO.
- Логи сохранения профиля содержат `request_id`, `user_id`, результат, код ошибки без PII-содержимого полей здоровья в открытом виде.
