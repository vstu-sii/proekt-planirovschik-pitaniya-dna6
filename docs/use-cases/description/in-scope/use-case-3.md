## 1. Идентификация
- **UC-3.** Сгенерировать персонализированное меню
- **Основной актор:** Пользователь
- **Дополнительные акторы:** AI-агент (GigaChat 2 Lite через адаптер), сервис валидации/расчётов, фиксированная БД «Мои продукты», БД планов питания
- **Триггер:** пользователь нажимает «Сгенерировать меню».
- **Приоритет:** Высокий
- **Частота:** 1 раз/неделя (план на 7 дней) или чаще для коротких планов

## 2. Связь со Спринтом 4
- **MVP-scope:** [mvp-scope.md](../../../sprint-4/mvp-scope.md) — UC-3 IN; блокирующие P0/P1 по G1-G3.

- **Связанные ID:** `BUG-018, BUG-020, BUG-021, BUG-022, BUG-023, BUG-025, BUG-019, BUG-024, BUG-026, BUG-004, BUG-E1, BUG-E3, BUG-E4, INFRA-04, INFRA-05, EVAL-01, SEC-01`.
- **Текущее состояние:** не принято; требуется реальный провайдер, детерминированная валидация, сохранение, safety и наблюдаемость.

## 3. Предусловия и выходные условия
**PRE-1.** Пользователь авторизован.  
**PRE-2.** Профиль валиден: бюджет, цель/КБЖУ, аллергены, предпочтения, время приготовления.  
**PRE-3.** Доступны каталог продуктов и сервис расчётов; AI-провайдер может быть временно недоступен — это обрабатываемый сбой.

**POST-1.** Валидный план питания на выбранный период сохранён в БД и привязан к `user_id`.  
**POST-2.** Сохранён и отображён список покупок, согласованный с планом и запасами.  
**POST-3.** Стоимость, КБЖУ и аллергены подтверждены серверной валидацией; источник чисел — backend-каталог/инструменты.  
**POST-4.** При техническом сбое/нарушении ограничений пользователь получает машинно-различимый ответ; небезопасный или неподтверждённый план не сохраняется как валидный.

## 4. Входной контракт

| Поле | Тип/формат | Обяз. | Правило |
|---|---|---:|---|
| `user_id` | UUID/string | да | Из сессии |
| `days` | integer/enum | да | Поддерживаемые значения периода (минимум 1/3/7 по продуктовой конфигурации); в Спринте 4 нельзя хардкодить 7 при выборе другого периода |
| `budget_week_rub` | number | да | Из профиля или подтверждённого ввода; `> 0` |
| `target_nutrition` | object | да | Целевое КБЖУ/БЖУ из профиля |
| `allergens` | string[] | нет | Жёсткие запреты |
| `preferences` | string[] | нет | Предпочтения/диета |
| `cooking_time_limit_min` | enum | нет | `15/30/null` |
| `inventory_product_ids` / `selected_products` | string[] | нет | Уже имеющиеся продукты; пустой список — валидный сценарий |

## 5. Выходной контракт: `MealPlanDraft` / сохранённый план

| Поле | Тип | Обяз. | Описание |
|---|---|---:|---|
| `plan_id` | UUID/string | да | Идентификатор сохранённого плана |
| `user_id` | UUID/string | да | Владелец плана |
| `days[]` | array | да | Дни плана; длина = `days` |
| `days[].meals[]` | array | да | Приёмы пищи/блюда дня |
| `meals[].ingredients[]` | array | да | Ингредиенты с `product_id`, количеством, единицей |
| `shopping_list[]` | array | да | Агрегированный список покупок с вычетом запасов |
| `totals.cost_planned_rub` | number | да | Прогнозируемая стоимость покупки по backend-каталогу |
| `totals.kcal_plan_total` / `pfc_plan_total` | number/object | да | Итоговые показатели плана |
| `totals.kcal_per_day[]` | array | да | Дневные КБЖУ отдельно от общих итогов |
| `validation` | object | да | Результат серверных проверок: бюджет, аллергены, КБЖУ, полнота данных |
| `warnings[]` | string[] | нет | Некритичные предупреждения, не маскирующие P0/P1 нарушения |

**Контрактное правило:** `totals` не смешивает стоимость покупки, КБЖУ плана и дневные показатели в одно неразмеченное число; поля именованы и проверяемы.

## 6. Контракт API / ошибок

| Сценарий | Поведение | Код/контракт |
|---|---|---|
| Успешная генерация | Валидный план сохранён и возвращён | `200/201` + `MealPlanDraft` |
| Невалидный запрос | Не хватает/некорректны поля (`days`, бюджет, профиль) | `400` + machine-readable error code |
| Нарушение ограничений | Нельзя уложиться в бюджет/аллергены/КБЖУ | `422` или эквивалент доменной ошибки; без сохранения небезопасного плана |
| Технический сбой провайдера/БД | Controlled degradation | `503` + `request_id`, retry policy по ADR-02 |
| Таймаут/частичный ответ | Не возвращать partial success как валидный план | `503/504` + `request_id` |

## 7. Основной сценарий
1. Пользователь открывает генерацию меню.
2. Система показывает ограничения профиля и выбор длительности.
3. Пользователь выбирает `days`, опционально отмечает имеющиеся продукты и подтверждает генерацию.
4. Backend формирует детерминированный контекст: профиль, каталог, запасы, ограничения.
5. AI-агент генерирует черновик плана; backend валидирует структуру `MealPlanDraft`.
6. Backend проверяет аллергены, бюджет, КБЖУ и рассчитывает `totals` по каталогу/инструментам.
7. При успехе план и список покупок сохраняются в БД.
8. UI показывает меню по дням, дневные КБЖУ, стоимость, список покупок и предупреждения.

## 8. Альтернативы и исключения
- **A1. Пустой список имеющихся продуктов:** валидный сценарий; генерация продолжается без учёта запасов.
- **A2. Повторная генерация:** создаёт новый план/версию по продуктовой политике; старый валидный план не портится молча.
- **E1. AI/каталог/БД недоступны:** `503` + `request_id`; mock `200` запрещён.
- **E2. Невозможно уложиться в ограничения:** доменная ошибка с причиной (`budget_exceeded`, `allergen_conflict`, `nutrition_unreachable` и т.п.); пользователь может скорректировать вход.
- **E3. Невалидный/небезопасный LLM output:** план отклоняется до сохранения; логируется причина и `request_id`.
- **E4. Перезагрузка после сохранения:** сохранённый план восстанавливается из БД (F5/new session).

## 9. Safety, валидация и деградация
- Аллергены и жёсткие запреты проверяются сервером после LLM; нарушение = fail-closed.
- Числа стоимости/КБЖУ считаются backend-инструментами по каталогу, не доверяются тексту модели.
- LLM output проходит schema validation перед бизнес-валидацией.
- При transient ошибке провайдера допускается 1 retry (ADR-02); далее controlled `503`.
- Логи/ответы не содержат секретов; PII минимизируется.

## 11. Наблюдаемость и NFR
- SLO: 95% успешных генераций < 10 с; SLA: 99% < 15 с (PRD/ADR).
- Логи: `request_id`, `user_id`, `days`, исход валидации, причина ошибки, latency, retries, provider mode.
- Метрики: success rate, validation fail rate, allergen block rate, p95 latency, 503 rate.
