## 3. Предусловия и выходные условия
**PRE-1.** Пользователь авторизован.  
**PRE-2.** Профиль настроен (бюджет/КБЖУ/ограничения) — для использования запасов в UC-3.

**POST-1.** Продукт добавлен/обновлён/удалён в запасах пользователя с количеством и сроком годности.  
**POST-2.** Изменения запасов доступны после перезагрузки и учитываются в следующей генерации/пересчёте.  
**POST-3.** При переносе из списка покупок товар помечен купленным, перенесён в запасы и не дублируется неконтролируемо.

## 5. Контракт интерфейса / API (v3)

| Операция | Контракт | Успех | Ошибки |
|---|---|---|---|
| Список запасов | `GET /inventory` | `200` + список, сортировка по сроку годности | `401` |
| Поиск в каталоге | `GET /products/search?q=` | `200` + варианты из фиксированной БД; пустой результат = валидный ответ | `400` короткий/невалидный запрос, `503` |
| Добавить запас | `POST /inventory` | `201` + созданная запись | `400` валидация, `409` дубликат/конфликт, `503` |
| Обновить запас | `PATCH/PUT /inventory/{id}` | `200` + обновлённая запись | `400`, `404`, `409`, `503` |
| Удалить запас | `DELETE /inventory/{id}` | `204/200` | `404`, `503` |
| Перенести из списка покупок | `POST /shopping-list/{id}/purchased` или batch | `200` + обновлённые запасы/список | `400`, `404`, `409`, `503` |

> Семантика обязательна: серверная валидация, машинно-различимые ошибки, идемпотентность для повторного «Куплено»/повторной отправки.

## 6. Основной сценарий
1. Пользователь открывает «Мои продукты».
2. Система показывает запасы, отсортированные по сроку годности.
3. Пользователь нажимает «Добавить продукт» и вводит название.
4. Система ищет в фиксированной локальной БД и показывает варианты.
5. Пользователь выбирает продукт; система подставляет единицу, категорию и рекомендуемый срок годности.
6. Пользователь подтверждает количество/срок и сохраняет.
7. Система валидирует и сохраняет запись в запасах пользователя.
8. Запись отображается в списке и доступна для UC-3.

## 7. Альтернативы и исключения
- **A1. Перенос из списка покупок:** товар(ы) помечаются «Куплено» → создаются/обновляются записи в запасах → товары удаляются/помечаются в списке покупок; повторный запрос не создаёт дубликат.
- **E1. Продукт не найден в каталоге:** поиск вернул пусто → пользователь может добавить ручную запись с обязательными КБЖУ/ценой/единицей или отменить; немой сбой недопустим.
- **E2. Дубликат:** существующий продукт найден по нормализованному ключу (`user_id`, `product_id`/нормализованное имя+единица) → система предлагает объединить количество или требует явного подтверждения.
- **E3. Некорректные данные:** `quantity <= 0`, невалидная дата/единица/КБЖУ → `400`, запись не сохраняется.
- **E4. Недоступность хранилища/каталога:** `503` + `request_id`; UI показывает ошибку и не подтверждает сохранение.

## 8. Правила валидации и состояния
- Нормализация имени обязательна перед поиском и сохранением.
- Дубликаты не создаются молча; поведение merge/confirm детерминировано.
- Изменение запасов после генерации UC-3 фиксируется в данных и учитывается при следующем расчёте/отображении.
- Продукты пользователя изолированы по `user_id`.
- Источник чисел по КБЖУ/цене для каталожных продуктов — фиксированная БД/бэкенд, не LLM.

## 10. Наблюдаемость и NFR
- Автоподстановка категории/срока годности ≤ 200 мс после выбора продукта.
- Логи операций содержат `request_id`, `user_id`, `product_id`, тип операции, результат; без лишних PII.
