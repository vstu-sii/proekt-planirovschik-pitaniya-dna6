**UC-1**. Настроить профиль
**Основной актор.** Пользователь
**Дополнительные акторы.** База данных профилей
**Описание.** Пользователь устанавливает или редактирует ключевые параметры своего профиля: параметры тела, недельный бюджет, целевое КБЖУ (или цель по весу, из которой КБЖУ рассчитывается автоматически), список аллергенов и пищевые предпочтения. Эти параметры становятся жесткими ограничениями для всех последующих генераций меню. 
**Триггер**. Пользователь нажимает кнопку «Настроить профиль» при первом входе в приложение или выбирает пункт «Мой профиль → Настройки питания» в главном меню.

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Приложение имеет доступ к интернету (для сохранения профиля).

**Выходные условия:**
	POST-1. Профиль пользователя сохранен в системе.
	POST-2. Новые ограничения применяются при следующей генерации меню. 

**Нормальное направление развития варианта использования:**
1.0 Настроить профиль и ограничения
	1. Пользователь открывает раздел «Настройки профиля».
	2. Система отображает текущие значения ограничений или пустые поля (при первом входе).
	3. Пользователь вводит недельный бюджет на питание (в ₽).
	4. Пользователь вводит параметры тела: пол (мужской или женский), вес (в килограммах), рост (в сантиметрах), возраст, уровень физической активности (коэффициент активности от сидячего до очень высокого).
	5. Пользователь выбирает цель: «Похудение» / «Поддержание массы» / «Набор массы».
	6. Система автоматически рассчитывает целевое КБЖУ с учетом цели и параметров тела и отображает его пользователю.
	7. Пользователь подтверждает рассчитанный КБЖУ или вручную корректирует его.
	8. Пользователь отмечает продукты-аллергены из справочника (например: «глютен», «лактоза», «арахис», «томаты» и т.д.).
	9. Пользователь выбирает пищевые предпочтения (например: «вегетарианство», «без глютена»).
	10. Пользователь нажимает «Сохранить».
	11. Система валидирует данные и сохраняет профиль.
	12. Система отображает сообщение: «Профиль сохранен. Попробуйте сгенерировать персонализированное меню».

**Альтернативное направление развития варианта использования:**
1.1 Ручной ввод КБЖУ вместо автоматического расчета
	1. Пользователь нажимает «Задать КБЖУ вручную».
	2. Пользователь вводит целевые значения калорий и макронутриентов самостоятельно.
	3. Система проверяет введенные значения, сравнивая с рекомендованными в соответствиями с параметрами тела и целями. 
	4а. Введенные значения проходят проверку, находясь в допустимом диапазоне (±20%).
	5а. Система принимает данные и сохраняет настройки профиля.  
	6а. Система продолжает нормальное направление варианта использования.
	4б. Введенные значения не проходят проверку и находятся за пределами допустимого диапазона (см. исключение 7.0.E5).

1.2 Редактирование существующего профиля
	1. Пользователь открывает раздел «Настройки профиля».
	2. Система отображает уже заполненные поля.
	3. Пользователь изменяет только часть полей.
	4. Система обновляет только измененные поля, остальные без изменений.
	5. Система продолжает нормальное направление варианта использования.

**Исключения:**
1.0.E1 Некорректные данные бюджета
	1. Пользователь вводит слишком маленький бюджет (< 1000 ₽/нед) или слишком большой бюджет (> 100 000 ₽/нед).
	2. Система отображает сообщение об ошибке: «Недельный бюджет должен быть в диапазоне от 1000 до 100 000 рублей».
	3a. Пользователь корректирует значение бюджета.
	4a.  Система продолжает начинает нормальное направление варианта использования.
	3б. Пользователь выходит из настроек профиля.
	4б. Система завершает вариант использования.

1.0.E2. Конфликт аллергенов и предпочтений
	1. Пользователь выбирает несовместимые параметры (например, «без глютена» + «мучное»).
	2. Система отображает предупреждение: «Выбранные параметры противоречат друг другу. Пожалуйста, измените выбор».
	3a. Пользователь корректирует выбор
	4а. Система продолжает начинает нормальное направление варианта использования.
	3б. Пользователь нажимает кнопку «Отмена».
	4б. Система завершает вариант использования.

1.0.E3. Недоступен сервер для сохранения профиля
	1. Пользователь нажимает «Сохранить». 
	2. Система не может сохранить профиль из-за проблем с сетью.
	3. Система отображает сообщение: «Не удалось сохранить профиль. Проверьте подключение к интернету и повторите попытку».
	4. Система завершает вариант использования.

1.0.E4 Пользователь не заполнил критически важные поля
	1. Пользователь нажимает «Сохранить», не указав критически важные поля.
	2. Система отображает сообщение: «Пожалуйста, укажите параметры {параметры} для продолжения».
	3. Система продолжает начинает нормальное направление варианта использования.

**Приоритет**: Высокий
**Частота использования**: 1 раз при первом входе, 1-2 раза в месяц для редактирования
**Бизнес-правила**: ACTION-05, CONSTRAINT-04, FACT-01
**Специальные требования**: Время отклика интерфейса ≤ 200 мс
**Предположения**: Справочник аллергенов и предпочтений содержит не менее 50 распространенных позиций. Пользователь при первом входе готов потратить 2–3 минуты на заполнение профиля.

**UC-2**. Пополнить локальную базу «Мои продукты»
**Основной актор.** Пользователь
**Дополнительные акторы.** Локальная база данных «Мои продукты», База данных RAG продуктов и цен
**Описание.** Пользователь добавляет, редактирует или удаляет продукты в локальной базе «Мои продукты». Это происходит вручную после похода в магазин. Система автоматически проставляет рекомендуемые сроки годности, опираясь на базу данных продуктов и цен. 
**Триггер**. Пользователь нажимает кнопку «Добавить продукт» в разделе «Мои продукты» ИЛИ нажимает кнопку «Куплено» напротив товара в «Списке покупок».

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.

**Выходные условия:**
	POST-1. Продукты добавлены в локальную базу с указанием количества и срока годности.

**Нормальное направление развития варианта использования:**
2.0 Добавить продукт в «Мои продукты»
	1. Пользователь переходит в раздел «Мои продукты» с главного экрана.
	2. Система отображает текущее содержимое раздела, продукты отсортированы по сроку годности.
	3. Пользователь нажимает кнопку «Добавить продукт».
	4. Пользователь начинает вводить название продукта.
	5. Система в реальном времени предлагает варианты из Глобальной базы RAG (например, при вводе «молоко» предлагает «Молоко 2.5%, 1 л»).
	6. Пользователь выбирает предложенный вариант.
	7. Система автоматически подставляет единицу измерения и рекомендуемый срок годности для данной категории продуктов (например, для открытого молока – 3 дня, для крупы – 180 дней), но позволяет пользователю изменить его при необходимости.
	8. Пользователь указывает количество (или подтверждает значение по умолчанию) и нажимает кнопку «Сохранить».
	9. Система сохраняет продукт в локальную базу «Мои продукты».

**Альтернативное направление развития варианта использования:**
2.1 Перенос из «Списка покупок»
	1. Пользователь открывает «Список покупок» (см. UC-1).
	2. Пользователь нажимает чекбокс «Куплено» напротив одного или нескольких товаров.
	3. Система перемещает эти товары в локальную базу «Мои продукты».
	4. Система автоматически назначает им стандартный срок годности на основе их категории из Глобальной базы RAG. 
	5. Система удаляет эти товары из «Списка покупок».

**Исключения:**
2.0.E1 Продукт не найден в Глобальной базе RAG
	1. Пользователь вводит название продукта.
	2. Система не находит совпадений в Глобальной базе RAG.
	3. Система отображает сообщение: «Не удалось найти продукт {продукт}. Добавить КБЖУ вручную?».
	4. Система предлагает пользователю скорректировать бюджет или КБЖУ.
	3a. Пользователь соглашается и добавляет стоимость и КБЖУ продукта.
	4a. Система продолжает нормальное направление варианта использования.
	3б. Пользователь отменяет добавление.
	4б. Система завершает вариант использования.

2.0.E2. Попытка добавить продукт, который уже есть в базе
	1. Система обнаруживает дубликат добавляемого продукта. 
	2. Система отображает сообщение: «Такой продукт уже есть в ваших запасах. Все равно добавить?».
	3a. Пользователь соглашается и увеличивает количество продукта в «Мои продукты».
	4a. Система продолжает нормальное направление варианта использования.
	3б. Пользователь отменяет добавление.
	4б. Система завершает вариант использования.

**Приоритет**: Высокий
**Частота использования**: 1-2 раза в неделю
**Бизнес-правила**: FACT-04, CONSTRAINT-05, COMPUTATION-03
**Специальные требования**: Автозаполнение срока годности по умолчанию должно срабатывать менее чем за 200 мс после выбора продукта из справочника. 
**Предположения**: Пользователь готов потратить минимум времени на ведение инвентаря, поэтому система максимально автоматизирует проставление сроков годности и единиц измерения, опираясь на категории продуктов. База данных RAG содержит актуальные цены и КБЖУ не старше 31 дней.

**UC-3**. Сгенерировать персонализированное меню
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, База данных RAG продуктов и цен 
**Описание.** Пользователь получает готовый план питания на выбранное количество дней (предустановлены 7 дней/3 дня/1 день), который строго укладывается в заданный бюджет, покрывает целевые КБЖУ, исключает запрещенные продукты-аллергены, учитывает предпочтения пользователя и то, что уже есть в его холодильнике.
**Триггер**. Пользователь нажимает кнопку «Сгенерировать меню»

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.

**Выходные условия:**
	POST-1. Меню на указанное количество дней (завтраки, обеды, ужины, перекусы) сохранено в системе.
	POST-2. Сформирован и сохранен список покупок.
	POST-3. Прогнозируемая стоимость меню меньше или равна заданному бюджету.

**Нормальное направление развития варианта использования:**
3.0 Инициировать генерацию меню
	1. Пользователь инициирует генерацию меню.
	2. Система отображает текущие ограничения из профиля и предлагает выбрать длительность плана для генерации меню (7/3/1 день).
	3. Пользователь выбирает длительность плана и отмечает продукты, которые уже есть дома.
	4. Пользователь подтверждает генерацию меню.
	5. Система формирует запрос к AI-агенту, учитывая ограничения по бюджету, КБЖУ, предпочтениям, аллергенам и имеющимся продуктам.
	6. Система проверяет каждое блюдо через RAG на ограничения.
	7. Система отображает итоговое меню с разбивкой по дням, общей стоимостью продуктов и дневным КБЖУ.

**Альтернативное направление развития варианта использования:**
3.1 Пропуск отметки имеющихся продуктов
	1. Пользователь пропускает этап отметки имеющихся продуктов.
	2. Система не учитывает имеющиеся продукты в запросе к AI-агенту. 

**Исключения:**
3.0.E1 Недоступен AI-агент или RAG-база
	1. Система не получает ответ от AI-агента в течение превышенного времени, установленном SLA (~15 секунд).
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже».
	3. Пользователь отменяет генерацию меню.
	4. Система завершает вариант использования.

3.0.E2 Невозможно уложить меню в бюджет с заданными ограничениями
	1. Система отображает сообщение: «Не удалось составить меню на {бюджет} ₽ с учетом всех ограничений».
	2. Система предлагает пользователю скорректировать бюджет или КБЖУ.
	3a. Пользователь корректирует бюджет или КБЖУ.
	4a. Система заново начинает нормальное направление варианта использования.
	3б. Пользователь отменяет генерацию меню.
	4б. Система завершает вариант использования.

**Приоритет**: Высокий
**Частота использования**: 1 раз в неделю на пользователя (генерация меню на 7 дней), 7 раз в неделю на пользователя (генерация меню на 1 день)
**Бизнес-правила**: CONSTRAINT-01, CONSTRAINT-02, CONSTRAINT-04, CONSTRAINT-05, CONSTRAINT-08, CONSTRAINT-09, COMPUTATION-03, FACT-03
**Специальные требования**: SLO < 10 сек (95% запросов), SLA < 15 сек (99% запросов)
**Предположения**: База данных RAG содержит актуальные цены и КБЖУ не старше 31 дней.

**UC-4**. Заменить блюдо
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, База данных RAG продуктов и цен
**Описание.** Пользователь заменяет одно конкретное блюдо в текущем меню на альтернативное, чтобы учесть изменившиеся предпочтения или обстоятельства, при этом система автоматически пересчитывает список покупок и контролирует соблюдение недельных ограничений бюджета и КБЖУ.
**Триггер**. Пользователь нажимает кнопку «Заменить блюдо» у конкретного приема пищи в меню.

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.
	PRE-3. У пользователя есть активное сгенерированное меню на выбранный промежуток генерации.

**Выходные условия:**
	POST-1. Выбранное блюдо заменено на альтернативное в меню.
	POST-2. Список покупок автоматически обновился.
	POST-3. Лимиты (бюджет и КБЖУ) остаются в рамках допустимых значений. 

**Нормальное направление развития варианта использования:**
4.0 Инициировать замену блюда
	1. Система отображает текущее блюдо и его параметры (КБЖУ, стоимость, ингредиенты).
	2. Пользователь выбирает конкретное блюдо в меню и нажимает «Заменить блюдо».
	3. Система формирует запрос к AI-агенту с условиями найти альтернативное блюдо со схожим КБЖУ и стоимостью с учетом ограничений профиля (аллергены, диеты).
	4. AI-агент возвращает 3 варианта альтернативных блюд с кратким описанием, КБЖУ и стоимостью.
	5. Система отображает пользователю список предложенных альтернатив.
	6. Пользователь выбирает один из предложенных вариантов.
	7. Система заменяет блюдо в меню.
	8. Система пересчитывает список покупок и прогнозирует итоговые КБЖУ и бюджет на неделю.
	9. Система показывает уведомление: «Блюдо заменено. Проверьте список покупок».

**Альтернативное направление развития варианта использования:**
4.1 Пользователь недоволен предложенными альтернативами
	1. На странице списка предложенных альтернатив пользователь нажимает «Предложить другие варианты».
	2. Система повторно запрашивает у AI-агента 3 новые альтернативы с расширенным коридором КБЖУ (±15%).
	3. Система продолжает нормальное направление варианта использования.

**Исключения:**
4.0.E1 AI-агент не нашел подходящих альтернатив
	1. AI-агент не может сгенерировать блюдо, удовлетворяющее всем условиям.
	2. Система отображает сообщение: «Не удалось найти подходящую замену с учетом всех ограничений».
	3. Система предлагает пользователю скорректировать бюджет или КБЖУ.
	3a. Пользователь корректирует бюджет или КБЖУ.
	4a. Система заново начинает нормальное направление варианта использования.
	3б. Пользователь отменяет генерацию замены.
	4б. Система завершает вариант использования.

4.0.E2 Замена нарушает недельные ограничения
	1. При пересчете списка покупок и прогнозировании итоговых КБЖУ и бюджета на неделю система обнаруживает, что бюджет превышен >20% или КБЖУ вышло за коридор ±15%.
	2. Система отображает сообщение-предупреждение: «Замена нарушит недельный бюджет/КБЖУ. Продолжить?».
	2a. Пользователь нажимает кнопку «Да».
	3a. Система применяет замену с пометкой нарушения ограничения. 
	4а. Система завершает вариант использования.
	2б. Пользователь нажимает кнопку «Нет».
	3б. Пользователь отменяет сгенерированную замену с нарушением ограничений.
	4б. Система предлагает пользователю скорректировать бюджет или КБЖУ. 
	5б. Система заново начинает нормальное направление варианта использования.

4.0.E3 Недоступен AI-агент или RAG-база
	1. Система не получает ответ от AI-агента в течение времени, установленном SLA (10 секунд).
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже».
	3. Пользователь отменяет генерацию меню.
	4. Система завершает вариант использования.

**Приоритет**: Высокий
**Частота использования**: 1-2 раза в неделю
**Бизнес-правила**: ACTION-01, CONSTRAINT-01, CONSTRAINT-02, CONSTRAINT-04, COMPUTATION-02
**Специальные требования**: SLO < 5 сек на генерацию альтернатив (95% запросов)
**Предположения**: RAG-база содержит достаточно рецептов для генерации альтернатив с учетом всех ограничений пользователя.

**UC-5**. Перенести меню
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, База данных RAG продуктов и цен 
**Описание.** Пользователь сдвигает все меню на выбранное количество дней N вперед (от 1 до 6 дней). Блюда каскадным сдвигом перемещаются в пределах текущего промежутка генерации; если последнее блюдо не помещается в границы текущего промежутка генерации, они удаляются из плана. Количество N дней, с которых был совершен сдвиг, остается пустым. Система пересчитывает список покупок и контролирует соблюдение недельных ограничений бюджета и КБЖУ.
**Триггер**. Пользователь нажимает кнопку «Перенести меню» в текущем меню.

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.
	PRE-3. У пользователя есть активное сгенерированное меню на выбранный промежуток генерации.

**Выходные условия:**
	POST-1. Все блюда меню сдвинуты на N дней вперед в пределах текущего промежутка генерации.
	POST-2. Блюдо, не поместившееся в границы выбранного промежутка генерации, удалены из плана. 
	POST-3. Список покупок автоматически обновился.
	POST-4. Лимиты (бюджет и КБЖУ) остаются в рамках допустимых значений. 
	POST-5. Первые N дней недели остались пустыми, не имея меню.

**Нормальное направление развития варианта использования:**
5.0 Инициировать сдвиг меню
	1. Пользователь нажимает кнопку «Перенести меню».
	2. Система отображает диалог выбора количества дней сдвига (от 1 до 6) с сообщением: «На сколько дней сдвинуть меню?».
	3. Пользователь выбирает N дней.
	4. Система отображает превью сдвига: список всех блюд с указанием, куда они переместятся.
	5. Система отображает сообщение-предупреждение: «Блюда, не поместившиеся в границы {выбранный промежуток}, будут удалены».
	6. Система запрашивает у пользователя подтверждение: Блюда последних {N} дней ({список названий}) будут удалены из плана. Продолжить?».
	7. Пользователь нажимает кнопку «Да», подтверждая сдвиг.
	8. Система выполняет каскадный сдвиг всех блюд на N дней вперед в пределах выбранного пользователем промежутка генерации. 
	9. Система удаляет не поместившиеся в границы блюда из плана.
	10. Система оставляет первые N дней пустыми. 
	11. Система пересчитывает список покупок и прогнозирует итоговые КБЖУ и бюджет на промежуток для генерации.
	12. Система показывает уведомление: «Меню сдвинуто на {N} дней. Удалено блюд: {количество}».  

**Альтернативное направление развития варианта использования:**
5.1 Пользователь передумал после превью
	1. Когда система предупреждает об удалении блюд, пользователь нажимает кнопку «Нет», отменяя сдвиг.
	2. Система завершает вариант использования.

5.2 Сегодня последний день промежутка генерации меню
	1. Пользователь нажимает кнопку «Перенести меню».
	2. Система отображает сообщение: «Сегодня последний день текущего меню. Сдвиг за пределы невозможен. Используйте "Заменить блюдо" для отдельных приемов пищи».
	3. Система завершает вариант использования.

5.3 Пользователь выбирает максимальный сдвиг (6 дней)
	1. Система отображает диалог выбора количества дней сдвига (от 1 до 6) с сообщением: «На сколько дней сдвинуть меню?».
	2. Пользователь выбирает 6 дней.
	3. Система отображает особое предупреждение: «При сдвиге на 6 дней будет удалено 6 из 7 дней меню. Продолжить?».
	4. Система продолжает нормальное направление варианта использования.

**Исключения:**
5.0.E1 Сдвиг нарушает недельные ограничения
	1. При пересчете списка покупок и прогнозировании итоговых КБЖУ и бюджета на неделю система обнаруживает, что бюджет превышен >20% или КБЖУ вышло за коридор ±10%.
	2. Система отображает сообщение-предупреждение: «Сдвиг нарушит недельный бюджет/КБЖУ. Продолжить?».
	2a. Пользователь нажимает кнопку «Да».
	3a. Система применяет замену с пометкой нарушения ограничения. 
	4а. Система завершает вариант использования.
	2б. Пользователь нажимает кнопку «Нет».
	3б. Пользователь отменяет сгенерированную замену с нарушением ограничений.
	4б. Система предлагает пользователю скорректировать бюджет или КБЖУ. 
	5б. Система заново начинает нормальное направление варианта использования.

5.2.E1 Блюда последнего дня приготовлены
	1. Пользователь нажимает кнопку «Перенести меню».
	2. Система обнаруживает, что в меню на последний день осталось менее 2 активных блюд.
	3. Система отображает сообщение: «В меню недостаточно блюд для сдвига. Сгенерируйте новое меню на неделю».
	4. Система завершает вариант использования.

**Приоритет**: Высокий
**Частота использования**: 1-2 раза в неделю
**Бизнес-правила**: ACTION-05, CONSTRAINT-01, CONSTRAINT-02, CONSTRAINT-03, CONSTRAINT-05, CONSTRAINT-15, CONSTRAINT-16, COMPUTATION-02, COMPUTATION-03, FACT-04
**Специальные требования**: Время пересчета меню ≤ 2 секунды
**Предположения**: Пользователь понимает, что сдвиг меню на N дней означает удаление последних N дней меню. Пустые дни пользователь заполнит через другие UC в течение недели.

**UC-6**. Сгенерировать рецепт из остатков
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, Локальная база данных продуктов пользователя «Мои продукты»
**Описание.** Пользователь вводит список оставшихся продуктов (автоматически из локальной базы «Мои продукты» с приоритетом скоропортящимся продуктам), и AI-агент генерирует рецепт с обязательным использованием этих ингредиентов, чтобы спасти продукты от выбрасывания. Система учитывает диетические ограничения и предпочтения пользователя из профиля. После выбора рецепта использованные продукты помечаются в локальной базе как «израсходованные».
**Триггер**. Пользователь нажимает кнопку «Zero-Waste Рецепт» на главном экране, ИЛИ система автоматически предлагает сгенерировать рецепт при наличии продуктов, срок годности которых истекает в течение 2 дней (push-уведомление).

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.

**Выходные условия:**
	POST-1. Пользователь получил 1-3 варианта рецептов с использованием указанных остатков.
	POST-2. Если в рецепте были дополнительные ингредиенты, не входившие в «Мои продукты», они добавляются в список покупок.

**Нормальное направление развития варианта использования:**
6.0 Инициировать генерацию меню из остатков
	1. Пользователь нажимает кнопку «Zero-Waste Рецепт» на главном экране, ИЛИ система автоматически предлагает сгенерировать рецепт при наличии продуктов, срок годности которых истекает в течение 2 дней (push-уведомление).
	2. Система отображает экран «Мои продукты» с продуктами, отсортированными по сроку годности. 
	3. Пользователь отмечает галочками продукты, которые хочет использовать, ИЛИ нажимает кнопку «Использовать все».
	4. Система формирует запрос к AI-агенту с условиями: обязательное использование указанных ингредиентов; соблюдение ограничений из профиля.
	5. AI-агент возвращает 3 варианта рецептов с пошаговой инструкцией, временем готовки и расчетом КБЖУ.
	6. Система отображает рецепты пользователю с указаниями: какие продукты будут использованы из списка «Мои продукты», какие дополнительные продукты нужно докупить, общая стоимость дополнительных продуктов.
	7. Пользователь выбирает один рецепт и нажимает «Подтвердить».
	8. Система отображает сообщение: «Рецепт сохранен».

**Альтернативное направление развития варианта использования:**
6.1 Пользователь пропускает этап отметки имеющихся продуктов
	1. Пользователь нажимает «Пропустить» на этапе отметки галочками оставшихся продуктов.
	2. Система не учитывает оставшиеся продукты в запросе к AI-агенту.
	3. AI-агент генерирует рецепты из базовых продуктов.
	4. Система продолжает нормальное направление варианта использования.

6.2 Push-уведомление при наличии скоропортящихся продуктов
	1. Система обнаруживает, что в локальной базе есть продукты со сроком годности ≤ 2 дней.
	2. Система отправляет push-уведомление: «Через {X} дней испортится {название продукта}. Приготовить что-то из него?»
	3. Пользователь нажимает на уведомление.
	4. Система продолжает нормальное направление варианта использования.

6.3 Пользователь недоволен предложенными рецептами
	1. Пользователь нажимает «Предложить другие варианты».
	2. Система повторно запрашивает у AI-агента 3 новых рецепта с расширенным списком допустимых дополнительных ингредиентов.
	3. Система продолжает нормальное направление варианта использования.

**Исключения:**
6.0.E1 Добавление базовых ингредиентов
	1. AI-агент не может собрать полноценный рецепт только из указанных остатков.
	2. Система отображает сообщение: «Разрешите добавление базовых ингредиентов (например, яйца, макароны, мука, масло) для большего выбора рецептов».
	3а. Пользователь нажимает кнопку «Да».
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь нажимает кнопку «Нет».
	4б. Система отображает сообщение: «Невозможно сгенерировать блюдо из этих продуктов. Попробуйте добавить еще ингредиенты или выберите другие продукты из остатков» (см. 5.0.E2).
	5б. Система завершает вариант использования. 

6.0.E2 AI-агент не может сгенерировать рецепт из указанных продуктов
	1. AI-агент не находит подходящих рецептов. 
	2. Система отображает сообщение: «Невозможно сгенерировать блюдо из этих продуктов. Попробуйте добавить еще ингредиенты или выберите другие продукты из остатков». 
	3а. Пользователь добавляет ингредиенты
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь изменяет список остатков.  
	4б. Система продолжает нормальное направление варианта использования.
	3в. Пользователь отменяет операцию с помощью кнопки «Отмена».
	4в. Система завершает вариант использования.

6.0.E3 Недоступен AI-агент или RAG-база
	1. Система не получает ответ от AI-агента в течение превышенного времени, установленном SLO (~15 секунд).
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже».
	3. Пользователь отменяет генерацию меню.
	4. Система завершает вариант использования.

6.0.E4. Указанные продукты содержат аллергены из профиля
	1. Пользователь вводит продукт, который входит в список его аллергенов.
	2. Система отображает предупреждение: «Вы указали продукт, на который у вас аллергия: {название}. Продолжить?»
	3а. Пользователь подтверждает осознанный выбор. 
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь удаляет продукт из списка.
	4б. Система продолжает нормальное направление варианта использования.

6.0.E5. Локальная база «Мои продукты» пуста
	1. Пользователь нажимает «Zero-Waste Рецепт».
	2. Система обнаруживает, что в локальной базе нет ни одного продукта.
	3. Система отображает сообщение: «У вас пока нет отмеченных запасов. Добавьте продукты вручную».
	4a. Пользователь выбирает «Добавить вручную».
	5а. Система продолжает нормальное направление варианта использования. 
	4б. Пользователь отменяет операцию с помощью кнопки «Отмена».
	5б. Система завершает вариант использования.

6.0.E6. Сроки годности всех продуктов в «Мои продукты» уже истекли
	1. Система обнаруживает, что все продукты в локальной базе с истекшим сроком годности.
	2. Система отображает предупреждение: «Сроки годности продуктов уже истекли. Удалите их из запасов».
	3. Пользователь подтверждает удаление просроченных продуктов. 
	4. Система очищает базу данных «Мои продукты». 
	5. Система продолжает нормальное направление варианта использования.

**Приоритет**: Средний
**Частота использования**: 2-4 раза в неделю на пользователя
**Бизнес-правила**: ACTION-02, FACT-04, CONSTRAINT-04, CONSTRAINT-10, CONSTRAINT-11, CONSTRAINT-15, CONSTRAINT-16, COMPUTATION-04, COMPUTATION-05, COMPUTATION-06
**Специальные требования**: SLO < 5 сек (95% запросов), SLA < 8 сек (99% запросов)
**Предположения**: Локальная база данных «Мои продукты» доступна. AI-агент имеет доступ к достаточно широкой базе рецептов, чтобы генерировать варианты из остатков. Пользователь честно указывает имеющиеся продукты.

	3. Система продолжает нормальное направление варианта использования.

**Исключения:**
7.0.E1 Добавление базовых ингредиентов
	1. AI-агент не может собрать полноценный рецепт только из указанных остатков.
	2. Система отображает сообщение: «Разрешите добавление базовых ингредиентов (например, яйца, макароны, мука, масло) для большего выбора рецептов».
	3а. Пользователь нажимает кнопку «Да».
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь нажимает кнопку «Нет».
	4б. Система отображает сообщение: «Невозможно сгенерировать блюдо из этих продуктов. Попробуйте добавить еще ингредиенты или выберите другие продукты из остатков» (см. 5.0.E2).
	5б. Система завершает вариант использования. 

7.0.E2 AI-агент не может сгенерировать рецепт из указанных продуктов
	1. AI-агент не находит подходящих рецептов. 
	2. Система отображает сообщение: «Невозможно сгенерировать блюдо из этих продуктов. Попробуйте добавить еще ингредиенты или выберите другие продукты из остатков». 
	3а. Пользователь добавляет ингредиенты
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь изменяет список остатков.  
	4б. Система продолжает нормальное направление варианта использования.
	3в. Пользователь отменяет операцию с помощью кнопки «Отмена».
	4в. Система завершает вариант использования.

7.0.E3 Недоступен AI-агент или RAG-база
	1. Система не получает ответ от AI-агента в течение превышенного времени, установленном SLO (~15 секунд).
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже».
	3. Пользователь отменяет генерацию меню.
	4. Система завершает вариант использования.

7.0.E4. Указанные продукты содержат аллергены из профиля
	1. Пользователь вводит продукт, который входит в список его аллергенов.
	2. Система отображает предупреждение: «Вы указали продукт, на который у вас аллергия: {название}. Продолжить?»
	3а. Пользователь подтверждает осознанный выбор. 
	4а. Система продолжает нормальное направление варианта использования.
	3б. Пользователь удаляет продукт из списка.
	4б. Система продолжает нормальное направление варианта использования.

7.0.E5. Локальная база «Мои продукты» пуста
	1. Пользователь нажимает «Zero-Waste Рецепт».
	2. Система обнаруживает, что в локальной базе нет ни одного продукта.
	3. Система отображает сообщение: «У вас пока нет отмеченных запасов. Добавьте продукты вручную».
	4a. Пользователь выбирает «Добавить вручную».
	5а. Система продолжает нормальное направление варианта использования. 
	4б. Пользователь отменяет операцию с помощью кнопки «Отмена».
	5б. Система завершает вариант использования.

**Приоритет**: Средний
**Частота использования**: 2-4 раза в неделю на пользователя
**Бизнес-правила**: ACTION-02, FACT-04, CONSTRAINT-04, CONSTRAINT-10, CONSTRAINT-11, CONSTRAINT-15, CONSTRAINT-16, COMPUTATION-04, COMPUTATION-05, COMPUTATION-06
**Специальные требования**: SLO < 5 сек (95% запросов), SLA < 8 сек (99% запросов)
**Предположения**: Локальная база данных «Мои продукты» доступна. AI-агент имеет доступ к достаточно широкой базе рецептов, чтобы генерировать варианты из остатков. Пользователь честно указывает имеющиеся продукты.

**UC-8**. Рассчитать КБЖУ блюда по фото
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, Модель компьютерного зрения
**Описание.** Пользователь фотографирует готовое блюдо, и система с помощью модели компьютерного зрения определяет основные видимые ингредиенты, оценивает примерный вес порции и рассчитывает КБЖУ. Функция является вспомогательной и не заменяет расчет КБЖУ, но значительно ускоряет процесс для пользователя, снижая усталость при ручном подсчете. Система обязана явно указывать пользователю уровень погрешности.
**Триггер**. Пользователь нажимает кнопку «Рассчитать КБЖУ по фото» в главном меню или на экране приготовленного блюда.

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.

**Выходные условия:**
	POST-1. Пользователь получил расчет КБЖУ блюда с явным указанием уровня погрешности.

**Нормальное направление развития варианта использования:**
8.0 Рассчитать КБЖУ блюда по фото
	1. Пользователь нажимает кнопку «Рассчитать КБЖУ по фото».
	2. Система открывает камеру или предлагает выбрать фото из галереи.
	3. Пользователь делает фотографию блюда или загружает готовое изображение.
	4. Система отправляет изображение в модель компьютерного зрения CV для анализа.
	5. CV-модель определяет основные видимые ингредиенты и оценивает примерный вес порции.
	6. Система сопоставляет определенные ингредиенты с базой данных КБЖУ RAG и рассчитывает суммарные калории, белки, жиры и углеводы.
	7. Система отображает результат пользователю с предупреждением о погрешности: «Примерно ~450 ккал, Б: 25 г, Ж: 15 г, У: 55 г. Погрешность оценки: ±20-30%».
	8. Система предлагает опции: «Скорректировать КБЖУ», «Попробовать еще раз», «Сохранить результат в меню».
	9. Пользователь нажимает кнопку «Сохранить результат в меню».
	10. Система сохраняет результат в меню.

**Альтернативное направление развития варианта использования:**
8.1 Пользователь корректирует результат вручную
	1. Пользователь нажимает кнопку «Скорректировать КБЖУ». 
	2. Система отображает список распознанных ингредиентов с возможностью редактирования веса каждого.
	3. Пользует корректирует состав блюда (например, добавляет «10 г оливкового масла», которое не было видно на фото).
	4. Система пересчитывает КБЖУ с учетом корректировок.
	5. Система продолжает нормальное направление варианта использования.

8.2 Пользователь пробует распознать КБЖУ еще раз
	1. Пользователь нажимает кнопку «Скорректировать КБЖУ». 
	2. Система продолжает нормальное направление варианта использования.

8.3 Пользователь фотографирует продукт, а не готовое блюдо
	1. Пользователь фотографирует упаковку продукта или сырой продукт (например, творог «Моя цена» или яблоко).
	2. Система продолжает нормальное направление варианта использования.

**Исключения:**
7.0.E1 Модель компьютерного зрения не может распознать блюдо
	1. Система отображает сообщение: «Не удалось распознать состав блюда. Сделайте фото еще раз при хорошем освещении или введите основные ингредиенты вручную».
	2а. Пользователь выбирает «Ввести вручную» (см. направление 6.1).
	2б. Пользователь отменяет операцию. 
	3б. Система завершает вариант использования.

8.0.E2 Недоступна модель CV или RAG-база
	1. Система не получает ответ от CV-модели или RAG-базы в течение превышенного времени, установленном SLA (~5 секунд).
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже или введите КБЖУ вручную».
	3а. Пользователь выбирает «Ввести вручную» (см. направление 6.1). 
	3б. Пользователь отменяет операцию. 
	4б. Система завершает вариант использования.

8.0.E3. Фото не содержит распознаваемых продуктов
	1. CV-модель не находит на фото ни одного продукта (например, фото пустой тарелки или напитка, который не распознается).
	2. Система отображает сообщение: «Невозможно распознать ингредиенты блюда. Повторите попытку».
	3а. Пользователь выбирает «Повторить».
	4а. Система заново начинает нормальное направление варианта использования.
	3б. Пользователь отменяет операцию. 
	4б. Система завершает вариант использования.

**Приоритет**: Низкий
**Частота использования**: 2-4 раза в неделю
**Бизнес-правила**: ACTION-04, CONSTRAINT-14, CONSTRAINT-12, CONSTRAINT-13
**Специальные требования**: SLO < 3 сек на распознавание и расчет (95% запросов); SLA < 5 сек (99% запросов); обязательное отображение уровня погрешности
**Предположения**: Модель CV обучена на достаточно разнообразной выборке блюд (≥ 10 000 изображений). База данных RAG содержит актуальные цены и КБЖУ не старше 31 дней. Пользователь понимает, что расчет КБЖУ по фото является приблизительным и не заменяет точное взвешивание продуктов.

**UC-9**. Выбрать блюдо из раздела «Коллекции»
**Основной актор.** Пользователь
**Дополнительные акторы.** AI-агент, База данных RAG продуктов и цен, База данных RAG рецептов
**Описание.** Пользователь открывает раздел «Коллекции» и выбирает структурированную подборку рецептов для конкретного сценария или уровня подготовки («Рецепты для новичков», «Вкуснее, чем доставка» и др.). Система отображает рецепты с учетом диетических ограничений пользователя из профиля. Каждый рецепт содержит пошаговую инструкцию и информацию о КБЖУ.
**Триггер**. Пользователь нажимает кнопку «Коллекции» в главном меню.

**Предварительные условия:**
	PRE-1. Пользователь авторизован.
	PRE-2. Профиль пользователя настроен, указаны ограничения: бюджет, КБЖУ, аллергены, предпочтения.

**Выходные условия:**
	POST-1. Пользователь выбрал рецепт из коллекции.
	POST-2. Рецепт добавлен в меню на определенный день.

**Нормальное направление развития варианта использования:**
9.0 Просмотреть коллекцию рецептов и выбрать блюдо
	1. Пользователь нажимает в меню кнопку «Коллекции».
	2. Система отображает список доступных коллекций с кратким описанием: например, «*Рецепты для новичков*» - простые блюда с пошаговыми инструкциями. «*Вкуснее, чем доставка*» - разнообразные рецепты (азиатская, мексиканская, итальянская кухня), которые готовятся за 30 минут. 
	3. Пользователь выбирает коллекцию (например, «Вкуснее, чем доставка»).
	4. Система фильтрует рецепты коллекции с учетом аллергенов и диет из профиля пользователя и отображает список рецептов с фото-превью, названием, временем готовки, КБЖУ и стоимостью.
	5. Пользователь выбирает рецепт.
	6. Система отображает подробный рецепт выбранного блюда.
	7. Система отображает кнопку «Добавить в меню». 
	8. Пользователь нажимает кнопку «Добавить в меню».
	9. Система предлагает выбрать день и прием пищи (завтрак/обед/ужин/перекус).
	10. Пользователь выбирает день и прием пищи.
	11. Система добавляет рецепт в меню и пересчитывает недельный бюджет и КБЖУ. 
	12. Система отображает уведомление: «Рецепт {прием пищи} добавлен в меню на {день}. Бюджет и КБЖУ недели обновлены».

**Альтернативное направление развития варианта использования:**
9.1 Пользователь не добавляет рецепт из коллекции
	1. Пользователь нажимает кнопку «Отмена».
	2. Система завершает вариант использования.

**Исключения:**
9.0.E1 В коллекции нет рецептов, подходящих под ограничения пользователя
	1. Система отображает сообщение: «Не удалось составить меню на {бюджет} ₽ с учетом всех ограничений».
	2. Система предлагает пользователю скорректировать бюджет или КБЖУ.
	3a. Пользователь корректирует бюджет или КБЖУ.
	4a. Система заново начинает нормальное направление варианта использования.
	3б. Пользователь отменяет генерацию меню.
	4б. Система завершает вариант использования.

9.0.E2. Недоступна база данных рецептов
	1. Система не может загрузить список рецептов в течение времени, установленного SLA.
	2. Система отображает сообщение: «Сервис временно недоступен. Попробуйте позже».
	3. Пользователь отменяет операцию. 
	4. Система завершает вариант использования.

9.0.E3. Пользователь не настроил профиль
	1. Система обнаруживает, что профиль пользователя не заполнен.
	2. Система отображает сообщение: «Для безопасного подбора рецептов рекомендуем заполнить профиль (аллергены, диеты). Сделать это сейчас?»
	3a. Пользователь нажимает «Заполнить профиль» 
	4а. Пользователь заполняет профиль (см. UC-7).
	5а. Система заново начинает нормальное направление варианта использования.
	3б. Пользователь нажимает «Пропустить» 
	4б. Система отображает сообщение-предупреждение: «Не удалось отфильтровать рецепты по вашим ограничениям.».
	5б. Система показывает все рецепты коллекции без фильтрации.

**Приоритет**: Низкий
**Частота использования**: 1-3 раза в неделю
**Бизнес-правила**: CONSTRAINT-04, CONSTRAINT-07, COMPUTATION-01, COMPUTATION-02, FACT-03
**Специальные требования**: Время отклика API ≤ 200 мс. Все рецепты в коллекции «Вкуснее, чем доставка» должны готовиться за 30 минут. Рецепты должны учитывать аллергены и диеты из профиля.
**Предположения**: База данных рецептов содержит ≥ 500 рецептов, распределенных по коллекциям.
