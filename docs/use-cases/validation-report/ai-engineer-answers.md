## Вопрос 1:
43/44 в отчете AI Engineer и 13/44 в Quality - это разные прогоны? Какие условия, датасет и модель использовались в каждом?
Ответ:
Да, результаты 43/44 и 13/44 нельзя считать показателями одного и того же испытания. В рамках моего испытания был выполнен отдельный запуск по Golden Dataset v1, состоящему из 44 тестовых кейсов. Для него использовалась модель `GigaChat-2`, а не заглушка.

Результат 43/44 относится к структурной валидности ответа: 43 ответа из 44 соответствовали JSON-формату и проверяемой структуре `{answer, assumptions, warnings}`. При этом все 44 обращения к API были успешными. Средняя задержка составила 1,523 секунды, среднее количество токенов — 366,34 на запрос.

Вывод: 43/44 следует считать результатом проверки структурированного ответа в испытании AI Engineer. 13/44 следует оставить отдельным результатом Quality до тех пор, пока команда не сопоставит конфигурации обоих запусков. Нельзя напрямую вычитать один показатель из другого или объявлять один из них ошибочным.

## Вопрос 2:
UI показывает КБЖУ и стоимость, а модель в eval их не выдаёт (`nutrition_info` 1/13, числовой `cost_ru_rub` 0/13 с числом). UI работает на другом пайплайне (backend-каталог) или модель должна отдавать эти поля?

Ответ:

Модель не должна быть источником достоверных значений стоимости и КБЖУ. Её задача — сформировать структурированный черновик меню: блюда, ингредиенты, их количество, тип приёма пищи и время приготовления.

Стоимость и пищевая ценность должны рассчитываться программно на основании каталога продуктов. Это необходимо по нескольким причинам:

1. Достоверность. LLM может сгенерировать правдоподобное, но фактически неверное число. Наличие числа в JSON ещё не делает его правильным.
2. Воспроизводимость. При одинаковых продуктах, количестве и версии каталога детерминированный расчёт должен давать одинаковый результат.
3. Контроль ограничений. Проверку бюджета и целевых значений КБЖУ можно выполнять программно, а не доверять модели, которая одновременно составляет меню и сама оценивает правильность собственной работы.
4. Обновление данных. Изменение цены или пищевой ценности продукта должно отражаться в расчёте через обновление каталога, без необходимости менять prompt или модель.

В отправленных в общий репозиторий это разделение уже отражено в коде. `baseline.py` формирует черновик `MealPlanDraft`, а `backend/routers/ai.py` содержит комментарий о том, что расчёты стоимости, КБЖУ и проверка ограничений должны выполняться детерминированными сервисами. Пока эти сервисы не подключены, API возвращает соответствующие значения как `null`, а `constraints_valid` не объявляет успешным.

Следовательно, если интерфейс показывает числовые КБЖУ и стоимость, эти данные не могут считаться результатом описанного в архиве AI-пайплайна. Вероятнее всего, UI получает их из отдельного backend-каталога, тестовых данных или другого расчётного механизма. Но сам архив не содержит кода UI и полного backend-каталога, поэтому точно установить фактический источник отображаемых значений по нему нельзя.

Модель отвечает за генерацию состава меню, backend — за числовые расчёты и формальную проверку. Это разделение должно быть отражено в контракте API и критериях приёмки UC-3.

## Вопрос 5:
`retrieval_metrics=N/A: no retriever integrated`. Ретривер отсутствует в eval-runner намеренно или это расхождение с целевым пайплайном?

Ответ:

Отсутствие retriever в eval-runner является намеренным архитектурным решением, а не ошибкой реализации тестового контура.

В первоначальном варианте рассматривалась возможность использования RAG, однако по итогам согласования требований от него отказались. В актуальной архитектуре MVP предполагается работа с фиксированной локальной базой «Мои продукты». Поэтому отдельный компонент векторного поиска и механизм retrieval не входят в текущий пайплайн.

Eval-runner проверяет работу модели на входных запросах из Golden Dataset v1. Он не выполняет поиск по векторной базе, поскольку такой компонент отсутствует в утверждённом объёме MVP. Следовательно, `retrieval_metrics=N/A` является корректным обозначением неприменимой метрики, а не нулевым результатом поиска.

При этом отсутствие RAG не означает, что модель должна самостоятельно придумывать состав продуктов, их стоимость или пищевую ценность. Эти сведения должны поступать из локального каталога и обрабатываться детерминированными инструментами backend.

## Вопрос 8:
Кто источник истины для КБЖУ и стоимости: ответ модели или backend-каталог?

Ответ:

Источником истины должен быть backend-каталог продуктов и детерминированные расчёты на его основе.

Модель не должна самостоятельно устанавливать точные цены и пищевую ценность продуктов. Она может предложить ингредиенты и количество, но для получения итоговых чисел backend должен сопоставить каждый ингредиент с записью локального каталога.

Предлагаемая последовательность:

1. AI формирует список ингредиентов с количеством.
2. Backend сопоставляет названия ингредиентов с продуктами из каталога.
3. Для каждого продукта получает стоимость и значения КБЖУ на заданную единицу измерения.
4. Пересчитывает показатели с учётом количества ингредиента.
5. Суммирует значения по блюдам и дням.
6. Проверяет итоговую стоимость и КБЖУ относительно пользовательских ограничений.
7. Возвращает рассчитанные значения вместе с результатом проверки.

Если продукт не найден в каталоге, backend не должен молча подставлять случайную цену или пищевую ценность. Такой ингредиент нужно пометить как неразрешённый, запросить уточнение или исключить из расчёта с явным предупреждением.

## Вопрос 9:
Что считать «безопасным отказом» и как его отличать от сбоя?

Ответ:
Безопасный отказ — это осознанный ответ системы на пользовательский запрос, который нельзя выполнить без риска нарушения ограничений, требований безопасности или достоверности результата.

Для планировщика питания такой отказ необходим в ситуациях, когда модель не может сформировать безопасную рекомендацию. Например:

- пользователь указывает аллергию, а система не может подтвердить отсутствие соответствующего аллергена в ингредиентах;
- ограничения пользователя противоречат друг другу;
- для корректной рекомендации недостаточно критически важных исходных данных;
- запрос требует медицинских гарантий или утверждений, которые система не может обоснованно предоставить;
- модель не может сформировать план, который одновременно соблюдает все обязательные ограничения.

| Ситуация                                        | Тип результата                             | Ожидаемое поведение                       |
| ----------------------------------------------- | ------------------------------------------ | ----------------------------------------- |
| Аллерген нельзя гарантированно исключить        | Безопасный отказ                           | Не выдавать неподтверждённое меню         |
| Недостаточно данных для безопасной рекомендации | Безопасный отказ или запрос уточнения      | Сообщить, каких данных не хватает         |
| Противоречивые ограничения                      | Отказ от генерации до устранения конфликта | Объяснить противоречие                    |
| Ошибка подключения к GigaChat                   | Технический сбой                           | Retry, затем контролируемая ошибка API    |
| HTTP 429                                        | Технический сбой / ограничение провайдера  | Ограниченный повтор с задержкой           |
| Некорректный JSON                               | Ошибка структурной генерации               | Повторная попытка и валидация             |
| Ошибка Pydantic                                 | Ошибка контракта                           | Не возвращать результат как валидный план |
| Тайм-аут                                        | Технический сбой                           | Вернуть соответствующую ошибку API        |

В текущем испытании проверялась прежде всего структура ответа. Сам факт прохождения JSON-валидации не подтверждает, что отказ действительно безопасен. Для этого необходимо отдельно оценивать safety-critical кейсы, проверять отсутствие опасных рекомендаций и проводить ручную экспертную проверку.

Вывод: безопасный отказ является допустимым функциональным результатом, если он вызван содержательным ограничением запроса и корректно объяснён пользователю. Ошибка API, тайм-аут или невалидный JSON безопасным отказом не являются.
