## 1. Задача AI Engineer

В рамках первой лабораторной работы необходимо было:
1. определить роль ИИ в проекте;
2. сформировать кандидатов моделей;
3. определить подход к интеграции LLM;
4. подготовить воспроизводимый эксперимент;
5. сравнить модели по объективным метрикам;
6. определить ограничения решения;
7. выбрать модель для MVP;
8. оценить токен-бюджет и стоимость выбранного решения.

## 2. Требования к AI-компоненту

AI-компонент должен получать параметры пользователя:
- цель питания;
- бюджет;
- срок планирования;
- ограничения и исключённые продукты;
- продукты, уже имеющиеся дома;
- максимальное время приготовления.

На выходе система должна формировать структурированный план питания.

Основные нефункциональные требования:
- время генерации — не более 30 секунд;
- ввод исходных данных — не более 3 минут;
- ответ — структурированный JSON;
- запрещённые продукты не должны попадать в результат;
- продукты из домашнего запаса следует использовать повторно;
- точная стоимость и КБЖУ рассчитываются программными инструментами.

## 3. Выбор моделей

На этапе подготовки были рассмотрены:
1. **GigaChat 2 Lite** — облачная API-модель;
2. **Qwen3-4B** — локальная open-source модель;
3. **Mistral Small** — облачная API-модель.

Количественное сравнение проведено для GigaChat 2 Lite и Qwen3-4B.
Mistral Small была подключена к эксперименту, но API возвращал:
```

HTTP 429 — Rate Limit Exceeded

```
Получить 9 сопоставимых запусков не удалось, поэтому Mistral не включалась в количественные таблицы и не использовалась для выбора модели.

## 4. Подход к решению

В эксперименте использовался следующий подход:
**Direct Prompt + Structured JSON + Python tools.**

LLM отвечает за:
- интерпретацию запроса;
- составление меню;
- выбор и комбинирование блюд;
- использование продуктов из pantry;
- формирование структурированного ответа.

Программные инструменты отвечают за:
- стоимость;
- КБЖУ;
- агрегацию ингредиентов;
- проверку ограничений;
- список покупок.

RAG и полноценный автономный агент отложены до следующего этапа.  

## 5. Тестовый system prompt

Каждая модель получала одинаковые требования:
- вернуть только JSON;
- сформировать план на 3 дня;
- учитывать бюджет и ограничения;
- использовать продукты из pantry;
- минимизировать остатки;
- не придумывать точную стоимость и КБЖУ;
- соблюдать заданную структуру данных.

Ответ проверялся через Pydantic-схему.

## 6. Тестовые сценарии
### A_basic — базовый сценарий

Студент хочет снизить вес.

Условия:
- бюджет — 2500 ₽ в неделю;
- без рыбы;
- в наличии гречка, яйца и курица;
- план на 3 дня;
- время приготовления блюда — не более 30 минут.

### B_budget — ограниченный бюджет

Молодой специалист хочет поддерживать вес.

Условия:
- бюджет — 2500 ₽ в неделю;
- в наличии морковь, курица и гречка;
- план на 3 дня.

### C_zero_waste — минимизация остатков

Пользователь хочет максимально использовать продукты, которые уже есть дома.

В наличии:
- 500 г моркови;
- 400 г курицы;
- 1 кг гречки.
Главное требование — минимизировать остатки.
Для каждого сценария выполнялось по 3 повтора.

## 7. Объём эксперимента

Фактически выполнено:
```

2 модели × 3 сценария × 3 повтора = 18 генераций

```

Распределение:
- GigaChat 2 Lite — 9;
- Qwen3-4B — 9.

Mistral Small — попытка запуска без сопоставимого набора данных.

## 8. Измеряемые метрики

| Метрика         | Что проверяет                                     |
| --------------- | ------------------------------------------------- |
| Latency         | время формирования ответа                         |
| JSON validity   | является ли ответ корректным JSON                 |
| Schema validity | соответствует ли ответ Pydantic-схеме             |
| Forbidden hits  | есть ли запрещённые продукты                      |
| Pantry mentions | насколько активно используются продукты из pantry |
| Within 30 sec   | соблюдается ли ограничение по времени             |
| Input tokens    | объём входного контекста                          |
| Output tokens   | объём сгенерированного ответа                     |
| Total tokens    | общий объём обработки                             |

Экспертная оценка качества меню не была сформирована, поэтому субъективные баллы в итоговые выводы не включались.

## 9. Надёжность и checkpoint

Во время предыдущего запуска эксперимента было обнаружено, что хранение результатов только в памяти через `results += run_repeats(...)` приводит к потере промежуточных данных при завершении сессии Colab.

Для итоговой версии notebook использован checkpoint-механизм.

После каждого завершённого запроса результат записывается в CSV.

В checkpoint сохраняются:
- модель;
- сценарий;
- номер повтора;
- latency;
- input/output/total tokens;
- JSON validity;
- schema validity;
- forbidden hits;
- pantry mentions;
- within 30 sec.

При повторном запуске уже завершённые комбинации `model + scenario + repeat` пропускаются.

Это позволяет продолжить эксперимент после остановки или ошибки среды.

## 11. Анализ результатов
### GigaChat 2 Lite

Средняя задержка составила 3,88 секунды.

Все 9 запусков уложились в требование не более 30 секунд.

JSON был корректным во всех запусках.

Соответствие Pydantic-схеме составило 88,9%. Единственный случай несоответствия пришёлся на `C_zero_waste`.

Запрещённых продуктов не обнаружено.

### Qwen3-4B

Qwen показал:
- 100% корректного JSON;
- 100% соответствия Pydantic-схеме;
- отсутствие запрещённых продуктов;
- большее среднее количество упоминаний pantry.

Однако средняя задержка составила 64,37 секунды, а ни один из 9 запусков не уложился в 30 секунд.

## 13. Что происходит при достижении лимита ответа

Параметр `max_tokens` ограничивает максимальную длину генерируемого ответа.

Если модель достигает этого ограничения, API GigaChat возвращает:
```

finish_reason = "length"

```
Это означает, что генерация остановлена по длине. Для проекта это может привести к неполному или невалидному JSON.

Поэтому в рабочей реализации необходимо:
1. проверить `finish_reason`;
2. проверить JSON;
3. проверить Pydantic-схему;
4. при ошибке выполнить повторную генерацию или запросить сокращённый ответ.

Не следует просто передавать пользователю результат, который закончился по `length`.

## 14. Что происходит при исчерпании общего лимита токенов

Это отдельная ситуация.

Если у API заканчиваются доступные токены конкретной модели, GigaChat возвращает HTTP:
```

402 Payment Required

```
После этого необходимо пополнить баланс или использовать доступный бесплатный лимит.

Для контроля бюджета приложение должно хранить статистику использования токенов и учитывать фактические значения `usage`.

Кроме того, слишком большой входной контекст также может вызвать ошибку. Поэтому необходимо контролировать размер system prompt, пользовательских данных, истории сообщений и подключаемых документов.

## 15. Стоимость выбранного решения

Для физического лица актуальный Freemium-режим GigaChat предоставляет **250 млн бесплатных токенов для моделей Lite на 12 месяцев**.

Для выбранной модели `GigaChat-2` это означает, что учебный прототип может работать без прямых расходов в пределах бесплатного лимита.

При переходе на платный пакет:
- 20 млн токенов GigaChat 2 Lite — 1300 ₽;
- стоимость — 65 ₽ за 1 млн токенов.

Средний фактический расход GigaChat в эксперименте:
```

791,8 токена / запрос

```
Ориентировочная стоимость одного аналогичного запроса по платному тарифу:
```

791,8 / 1 000 000 × 65 ≈ 0,052 ₽

```
Ориентировочная стоимость 1000 таких запросов:
```

≈ 51,47 ₽

```
Ориентировочная стоимость 10 000 таких запросов:
```

≈ 514,67 ₽

```
Фактический расход 9 тестовых запусков GigaChat:
```

≈ 7 126 токенов

≈ 0,46 ₽ по платному тарифу

```
Для Qwen3-4B API-тарификации нет: модель запускалась локально на Tesla T4. Поэтому расходы связаны не с количеством токенов, а с вычислительным ресурсом и временем работы GPU-среды.

## 16. Итоговый выбор

Для MVP выбрана:

**GigaChat 2 Lite.**

Основание выбора — выполнение ключевого нефункционального требования по скорости:
- средняя задержка — 3,88 секунды;
- 100% запусков — не более 30 секунд.

Qwen3-4B остаётся альтернативным локальным вариантом:
- сильная структурная стабильность;
- 100% соответствие схеме;
- большее использование pantry;
- но средняя задержка 64,37 секунды.

Эксперимент не позволяет утверждать, что GigaChat лучше по общей «качественности» меню, поскольку экспертная оценка качества не была собрана. Выбор относится именно к требованиям текущего MVP.

## 17. Архитектурное решение

Итоговая схема:
```

Пользователь

    ↓

GigaChat 2 Lite

    ↓

Structured JSON

    ↓

Pydantic validation

    ↓

Python / DB tools

    ├─ calculate_cost

    ├─ calculate_nutrition

    ├─ aggregate_ingredients

    ├─ validate_constraints

    └─ build_shopping_list

    ↓

Итоговый план питания

```
При ошибке:
```

LLM response

    ↓

JSON validation

    ↓

ошибка?

 ┌──┴──┐

да    нет

 ↓      ↓

retry  tools

 ↓      ↓

валидный результат

```

## 18. Ограничения эксперимента

- только два кандидата получили полный количественный набор результатов;
- Mistral Small не удалось полноценно протестировать из-за HTTP 429;
- использовано три тестовых сценария;
- по каждому сценарию выполнено только три повтора;
- экспертная оценка качества не была собрана;
- Qwen тестировался на конкретной конфигурации Tesla T4, поэтому его latency нельзя автоматически переносить на другую GPU;
- база рецептов и продуктов ещё не подключена.
