# Lab 2 — Spike experiments

## 1. Цель

В Lab 1 GigaChat 2 Lite была выбрана для MVP по техническим показателям: средняя задержка 3,88 с и 100% запусков в пределах 30 с. В Lab 2 проверялись два дополнительных предположения: модель может одновременно соблюдать несколько ограничений, а корректирующий запрос может исправлять невалидный ответ.

Эксперименты выполнены на **одном тестовом запросе** в GigaChat 2 Lite. Поэтому результаты являются предварительной проверкой конкретного сценария, а не статистическим подтверждением надёжности модели.

## 2. Эксперимент A — несколько ограничений

**Гипотеза:** при одном прямом prompt модель вернёт план, который проходит проверку JSON, Pydantic-схемы, запрещённых продуктов и времени приготовления, а также использует продукты из pantry.

**Условия запуска:**
- модель: GigaChat API, параметр модели в ноутбуке — `GigaChat-2`;
- подход: Direct Prompt + Structured JSON;
- число запросов: 1;
- длительность плана: 3 дня;
- цель: поддержание веса;
- бюджет в запросе: 2500 RUB/неделю;
- запрещённые продукты: рыба и арахис;
- продукты дома: гречка, яйца, курица;
- максимальное время приготовления: 30 минут.

**Фактические результаты:**

| Проверка | Результат |
|---|---|
| Ответ получен | Да (`status: ok`) |
| Задержка вызова модели | 5,70 с |
| `finish_reason` | `stop` |
| JSON разбирается | Да |
| Pydantic-схема проходит | Да |
| Найдены запрещённые продукты | Нет |
| Блюда превышают 30 минут | Нет |
| Продукты pantry найдены в плане | Все три: гречка, яйца, курица |

**Вывод по Spike A: сработало в данном тестовом сценарии.** Ответ прошёл реализованные автоматические проверки и содержал все три продукта из pantry. Время вызова модели составило около 5,70 секунды, что меньше целевого ограничения 30 секунд.

Ограничения интерпретации: тест выполнен один раз; проверка запрещённых продуктов основана на поиске названий в ингредиентах; проверка времени использует поле `cook_time_min`, заявленное самой моделью. Код этого эксперимента **не проверяет фактическое соблюдение бюджета**, не подтверждает питательную ценность меню и не оценивает его кулинарную полезность. Поэтому результат не доказывает полное соблюдение всех продуктовых требований.

## 3. Эксперимент B — корректирующий запрос

**Гипотеза:** если первичный ответ не проходит schema/constraint validation, один корректирующий запрос с перечислением обнаруженных нарушений может исправить его.

Ноутбук запускает retry только в том случае, если первичный ответ не проходит проверки. В фактическом запуске первичный ответ прошёл проверку схемы и реализованные проверки ограничений:

- `schema_valid: true`;
- `constraints_valid: true`;
- `forbidden_hits: []`;
- `long_meals: []`.

Поэтому результат Spike B: **`not_needed` — корректирующий запрос не выполнялся**.

Это не подтверждает и не опровергает эффективность corrective prompt. Для проверки гипотезы необходимо получить первичный ответ с обнаруженным нарушением или подготовить отдельный контролируемый тест с заведомо невалидным ответом, после чего сравнить результаты до и после одного retry.

## 4. Общий вывод по экспериментам

1. **Spike A — сработало в одном тестовом случае:** GigaChat вернула разбираемый JSON, прошла Pydantic-валидацию, в проверенных ингредиентах не обнаружены рыба и арахис, превышения заявленного времени приготовления не выявлены, в плане присутствуют гречка, яйца и курица. Задержка — 5,70 с.
2. **Spike B — не проверен (`not_needed`):** первичный ответ оказался валидным по реализованным проверкам, поэтому повторный корректирующий вызов не понадобился. Нельзя заявлять, что retry исправляет ошибки.
3. Из-за размера выборки **n = 1** результаты предварительные и не гарантируют повторяемость на других запросах.
4. Проверка бюджета в этом ноутбуке отсутствует. Хотя бюджет передан модели в prompt, эксперимент не рассчитывает стоимость и не проверяет её программно. Точные стоимость и КБЖУ должны рассчитываться отдельными инструментами и проверяться до выдачи результата пользователю.

## 5. Влияние на архитектуру

Результат Spike A поддерживает использование прямого prompt со структурированным JSON для прототипа, но не отменяет независимые программные проверки. Перед production нужно расширить Golden Dataset и проверить больше сценариев, включая сложные сочетания ограничений и отрицательные случаи.

В `docs/ai-pipeline.md` следует оставить schema validation и constraint validation обязательными этапами. Один corrective retry можно оставить как **предусмотренный, но пока экспериментально не подтверждённый** механизм восстановления. Если после повторной проверки план невалиден, система должна вернуть контролируемую ошибку, а не выдавать неподтверждённый план.
