# Lab 3 — Baseline: фактические результаты и план повторного eval

## 1. Цель и границы отчёта

Цель — зафиксировать поведение работающей baseline-модели на Golden Dataset, измерить доступные технические метрики и определить, какие выводы допустимы для продукта.

В этом архиве есть **исторический прогон 44 кейсов**, но нет утверждённого исходного файла `docs/quality/golden-dataset/v1.json`. Поэтому воспроизводимый повторный прогон подготовлен в ноутбуке и runner, но **новые результаты пока не получены**. Никакие значения исторического запуска не выдаются за результаты исправленного запуска.

## 2. Почему в прогоне использовалась GigaChat-2

В Lab 1 для сравнения использовалась GigaChat 2 Lite. В ходе подготовки Golden Dataset при подключении к GigaChat 2 Lite возникла ошибка подключения, поэтому модель в ноутбуке была переименована/переключена на `GigaChat-2`, чтобы выполнить прогон.

Это операционное решение для проведения эксперимента, а не доказательство эквивалентности моделей и не пересмотр ADR на основании сравнительного теста. Новый runner и baseline сохраняют `GigaChat-2` как значение по умолчанию, но позволяют задать фактически доступную модель переменной `GIGACHAT_MODEL`. В отчёте каждого запуска необходимо фиксировать точное значение.

## 3. Исторический прогон (обычный текстовый режим)

Исходные файлы сохранены в `docs/experiments/historical/` и не перезаписываются исправленным кодом. Из исходного summary:

- кейсов: 44;
- запросов, отмеченных как успешные: 44 из 44 (100%);
- средняя задержка: 1,935 с;
- медианная задержка: 1,554 с;
- минимум: 0,552 с;
- максимум: 6,751 с;
- JSON validity: не измерялась (`null`), поскольку `STRUCTURED_MODE = False`;\n- в сохранённом объекте ответа присутствует provider model identifier `GigaChat-2:2.0.30.01` (алиас настройки — `GigaChat-2`);
- буквальный `must_contain` pass rate: 0%;
- буквальный `must_not_contain` pass rate: 100%.

### Как интерпретировать эти значения

100% API success означает только, что исходный ноутбук не зафиксировал исключение API для 44 запросов. Это не означает 100% корректных ответов. В исторических результатах использовался `str(response)` при отсутствии `response.text`; поэтому поле `raw_response` могло содержать метаданные SDK вместе с ответом. Текстовые и буквальные метрики старого запуска нельзя считать надёжной оценкой качества.

Нулевой буквальный `must_contain` pass rate также не доказывает автоматически, что каждый ответ плохой: буквальный поиск не распознаёт синонимы, склонения и смысловую эквивалентность. Для этих критериев нужна ручная/семантическая оценка. `must_not_contain` не заменяет полноценную проверку безопасности.

В датасете есть кейсы `safety_critical`. Их статус человеческой проверки — `pending`; они не считаются экспертно одобренными.

## 4. Что изменено в коде

- `ml/models/baseline.py`: извлекается только `response.choices[0].message.content`; usage tokens читаются из SDK, если доступны; успешные и неуспешные вызовы передаются в tracer; имя модели задаётся `GIGACHAT_MODEL` (по умолчанию `GigaChat-2` с учётом ошибки подключения, описанной выше).
- `ml/tracing/tracer.py`: JSONL-трейсы включают модель, request ID, latency, статус, попытку, токены и ошибки. Сохранение содержимого промпта/ответа отключено по умолчанию; его можно включить `TRACE_CAPTURE_CONTENT=true` после проверки требований приватности.
- `backend/routers/ai.py`: обработчик асинхронный, вызов синхронного SDK вынесен в thread pool, вход проверяется Pydantic-моделью. Стоимость и КБЖУ больше не маскируются нулями: пока детерминированные инструменты не подключены, они возвращаются как `null`, а проверка ограничений явно не объявляется успешной.
- `tests/evals/run_golden.py`: добавлен повторяемый runner с JSON-обёрткой `{answer, assumptions, warnings}`, извлечением usage, latency на кейс, ограниченными retry и записью трасс. Retry повторяет запрос с тем же prompt; эффективность специального corrective prompt этим кодом не проверяется.
- `docs/experiments/lab3_golden_eval.ipynb`: подготовлен к повторному прогону в Colab, очищены старые outputs, чтобы исторические результаты не выглядели как результаты нового запуска.

## 5. Как выполнить новый прогон

### Вариант A — Google Colab

1. Откройте `docs/experiments/lab3_golden_eval.ipynb`.
2. Передайте `GIGACHAT_CREDENTIALS` через скрытый ввод; не записывайте секрет в ячейку или файл.
3. Загрузите утверждённый командой `v1.json` из Golden Dataset. Не восстанавливайте эталонный датасет из ответов модели.
4. Проверьте, что в выводе `MODEL_NAME` совпадает с реально используемой моделью. При необходимости задайте `GIGACHAT_MODEL`.
5. Выполните все ячейки сверху вниз. Скачайте JSON, CSV, summary и JSONL traces.
6. Скопируйте новые результаты в репозиторий как отдельные текущие артефакты; не заменяйте каталог `historical`.

### Вариант B — локальный runner

После добавления утверждённого `v1.json` и настройки переменных окружения:

```bash
export GIGACHAT_CREDENTIALS="..."
export GIGACHAT_MODEL="GigaChat-2"
python tests/evals/run_golden.py   --dataset docs/quality/golden-dataset/v1.json   --out docs/experiments/golden_eval_current.json   --summary-out docs/experiments/golden_eval_current_summary.json   --csv-out docs/experiments/golden_eval_current.csv
```

В Windows PowerShell используйте `$env:GIGACHAT_CREDENTIALS="..."` и `$env:GIGACHAT_MODEL="GigaChat-2"`. Не коммитьте значение credentials.

Runner завершится с понятной ошибкой, если датасет или credentials отсутствуют. Это намеренно: он не должен выдавать фиктивный результат.

## 6. Что измеряется новым запуском

- API/provider success;
- валидность JSON-ответа;
- соответствие Pydantic-схеме оболочки `{answer, assumptions, warnings}`;
- latency каждого кейса, средняя/медианная/min/max задержка;
- input/output/total tokens, если SDK возвращает usage;
- буквальные проверки `must_contain` и `must_not_contain`;
- ошибки и число попыток;
- трассы каждого вызова.

**Ограничение:** схема-обёртка eval runner не равна полному контракту `MealPlanDraft` API. Её валидность не доказывает корректность меню, точность стоимости/КБЖУ, соблюдение диетических ограничений или медицинскую безопасность. Эти свойства должны оцениваться отдельными автоматическими проверками и/или человеком.

## 6.1. Трассировка LLM-вызовов

Исправлена трассировка в двух путях запуска:

- `ml/tracing/tracer.py` по умолчанию сохраняет `prompt` и `response` (`TRACE_CAPTURE_CONTENT=true`);
- `docs/experiments/lab3.ipynb` теперь передаёт prompt и response в каждую запись trace как для успешных, так и для ошибочных попыток;
- `docs/experiments/llm_traces.jsonl` содержит 48 событий исходной сессии: smoke-test и все попытки 44 кейсов;
- `artifacts/traces.jsonl` содержит ту же трассу в стандартном пути.

Для ошибочных попыток, где исходная сессия не сохранила тело ответа в результатах, `response` оставлен `null` с явным `response_capture_status`; сам вызов, prompt, latency, ошибка и номер попытки при этом видны. Нельзя честно восстановить ответ, который старый код выбросил, потому что даже компьютеры не умеют читать прошлое.

## 8. Что это значит для продукта

Исторический прогон показывает, что модель отвечала быстро в условиях того запуска. Он не доказывает, что ответы соответствуют требованиям продукта: структурированный формат не проверялся, а буквальные критерии не прошли.

До использования плана в интерфейсе необходимо:
1. валидировать вход и структурированный выход;
2. считать стоимость и КБЖУ детерминированными инструментами;
3. проверять запрещённые продукты и ограничения программно;
4. не выдавать черновик за проверенный план;
5. оценить ошибки на Golden Dataset, отдельно обработав safety-critical кейсы;
6. только после этого устанавливать пороги регрессии для CI.

## 9. Следующие шаги

3. Сверить метрики с предыдущими экспериментами, явно отметив, что модель могла отличаться от Lab 1.
4. Провести ручную оценку семантических и safety-кейсов.
5. На основе реальных результатов согласовать порог CI и обновить Golden Dataset v2.
6. Согласовать с Delivery контракт ответа API, пока значения totals не рассчитываются.
