# ADR-02: Выбор и интеграция основной LLM-модели для MVP

## Статус

## Контекст (Context)
Системе требуется LLM для смысловой генерации персонализированного меню в рамках паттерна *Direct Prompt + Structured JSON + Python tools*.

Критическое нефункциональное ограничение: пользовательский сценарий генерации должен укладываться в 30 секунд. В Lab 1 были протестированы три кандидата: GigaChat 2 Lite (облачный API), Qwen3-4B (локальный запуск) и Mistral Small (облачный API).

Подробные количественные метрики, ограничения эксперимента и обоснование выбора зафиксированы в отдельном Model ADR: `docs/model-candidates.md`. Данный архитектурный ADR фиксирует решение о том, *как* выбранная модель интегрируется в систему и какие архитектурные паттерны применяются для обеспечения отказоустойчивости.

## Решение (Decision)
1. Использовать **GigaChat 2 Lite** (внешний облачный API Sber) в качестве основного LLM-адаптера для MVP.

2. Реализовать архитектурный паттерн контролируемой деградации:

   - Основной вызов GigaChat с жестким таймаутом.

   - При transient error допускается ровно один повтор (retry) на уровне сервиса, если это не нарушает общий таймаут.

   - При недоступности модели система возвращает контролируемую ошибку `503 Service Unavailable` с `request_id`, а не бесконечное ожидание или «сырой» ответ.

1. Локальные модели (Qwen3-4B) и альтернативные API (Mistral) не включаются в контур MVP как автоматический fallback из-за неподтвержденного SLO (64 сек для Qwen) или проблем с rate-limits (HTTP 429 для Mistral).

2. Реализовать LLM-вызовы через интерфейс адаптера (абстракцию), чтобы в будущих релизах подключить альтернативные модели без переписывания ядра AI-пайплайна.
## Последствия (Consequences)
#### Плюсы (+)
- Гарантированное соблюдение SLO по latency (среднее время ответа 3.88 сек, 100% запросов ≤ 30 сек).
- Отсутствие необходимости развертывания и обслуживания GPU-инфраструктуры для inference на стороне проекта.
- Упрощение архитектуры бэкенда и CI/CD (нет тяжелых артефактов весов моделей в репозитории).

#### Минусы (-)
- Появление жесткой внешней зависимости: сеть, доступность API провайдера, rate limits.
- Необходимость обязательной программной валидации JSON-схемы (Pydantic) и реализации retry-логики на уровне AI-пайплайна, так как schema validity в Lab 1 составила 88.9%.
- Ограниченный контроль над обновлениями базовой модели со стороны провайдера.

## Цена решения (Decision Cost)
- **Финансовая:** Зависимость от тарификации внешнего провайдера. По данным Lab 1, средний расход составляет ~791.8 токена на запрос, что оценивается в ~0.052 ₽ за запрос при платной тарификации.
- **Архитектурная:** Система не сможет работать в режиме офлайн. При падении внешнего API функция генерации меню будет полностью недоступна.
- **Технический долг:** Необходимость написания и поддержки абстракции (адаптера) для LLM, чтобы минимизировать затраты на интеграцию Qwen3-4B или Mistral в Релизе 2.0/3.0.
