# ERD — «Планировщик питания»

## Назначение

`erd.puml` содержит логическую ER-диаграмму данных MVP. Она описывает, как можно хранить профильные ограничения пользователя, продукты и pantry, сформированные планы питания и список покупок. Это проектная модель для согласования с командой, а не утверждение о том, что все таблицы уже реализованы в работающей БД.

## Сущности и связи

- **User** — пользователь приложения.
- **MealPlan** — созданный план питания: цель, бюджет, валюта, число дней и лимит времени приготовления.
- **DietaryRestriction** — диетические ограничения пользователя.
- **ExcludedProduct** — продукты, явно исключённые пользователем.
- **Product** — справочник продуктов с ориентировочной ценой и КБЖУ на 100 г.
- **PantryItem** — количество продукта, уже имеющееся у пользователя.
- **DayPlan** — отдельный день плана.
- **Meal** — приём пищи в конкретный день.
- **MealIngredient** — связь блюда с продуктом и количеством ингредиента.
- **ShoppingListItem** — рассчитанная потребность в продукте для покупок и её оценочная стоимость.

## Основные правила модели

1. Один пользователь может иметь несколько планов питания, ограничений, исключённых продуктов и записей pantry.
2. План включает один или несколько дней; день включает одно или несколько блюд.
3. Блюдо содержит ингредиенты через связующую сущность `MealIngredient`, поскольку один продукт может использоваться во многих блюдах, а одно блюдо состоит из нескольких продуктов.
4. Список покупок связан с планом и справочником продуктов. Количество для покупки рассчитывается с учётом ингредиентов плана и pantry.
5. Цена и КБЖУ хранятся в справочнике как исходные значения; итоговые суммы и показатели плана вычисляются программными инструментами, а не принимаются на веру из ответа LLM.
6. `DietaryRestriction` и `ExcludedProduct` представлены отдельно: первое хранит обобщённые требования, второе — конкретные запрещённые продукты.

## Согласование с AI API

Контракт `api/openapi.yaml` описывает транспортный запрос/ответ для `POST /api/v1/ai/meal-plans`. ERD описывает предполагаемое постоянное хранение данных приложения. Поля `goal`, `budget`, `days`, `max_cook_time_min`, `restrictions`, `excluded_products` и `pantry` из запроса преобразуются в данные соответствующих сущностей/связей; `days`, `meals`, `ingredients`, `shopping_list` и `totals` ответа формируются из плана, справочника продуктов и результатов расчётов.

Идентификатор пользователя в текущем AI API не передаётся: привязка к `User` должна выполняться уровнем приложения/авторизации либо быть согласована с Delivery при расширении контракта. В рамках MVP AI-компонент не вводит отдельную БД.
